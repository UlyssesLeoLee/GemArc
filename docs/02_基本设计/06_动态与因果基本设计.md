## 4D 运行模型

4D 不表示“3D 的旋转动画”，而是状态机与事件驱动的模型化执行。

- `Scenario`：版本化环境、输入、随机种子、事件上限与结果。
- `Event`：事件序号、逻辑时间、source、target、type、payloadHash、依据。
- `StateTransition`：前置状态、触发条件、后置状态和副作用。
- `Timeline`：可暂停、seek、逐事件重播；不把 UI 帧率视作业务运行时延。

## 5D 因果推演

- 输入：若干 4D 模块、连接规则、干预、假设和证据。
- 处理：验证组件输入输出类型→构建有向影响图→按定义顺序处理事件→生成解释链→比较基线与干预。
- 输出：Outcome、ImpactGraph、difference、assumptions、evidenceRefs、limitations。
- 反馈环路必须明确时间展开或设置收敛/次数阈值；不可直接当普通无环因果图推断。

## 标准场景模板

| Case | 起点 | 干预 | 预期（设计模型假设） |
|---|---|---|---|
| CASE-001 正常执行 | 请求→队列→规则→通知 | 无 | 在已定义条件下到达通知事件 |
| CASE-002 队列超时 | 请求进入队列 | 超过超时阈值 | 超时后转入失败/重试分支 |
| CASE-003 规则服务故障 | 已接收到事件 | 禁用规则模块 | 下游事件按依赖规则中断，并报告受影响节点 |
| CASE-004 恢复/补偿 | 失败状态 | 启用补偿策略 | 在规定条件内恢复或终止 |

以上是**组件测试用的假设示例**，不代表用户真实仓库存在上述模块。缺少被验证的业务规则时必须禁止生成确定性事实结论。
