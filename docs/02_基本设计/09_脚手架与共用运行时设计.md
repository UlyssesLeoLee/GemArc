# 5D 脚手架与共用运行时设计

> 文档编号：BD-009 ｜版本：1.0 ｜日期：2026-10-25 ｜状态：已实现（Python 侧与浏览器侧均有自动化测试）  
> 产品：GemArc MCP — 5D Design Scaffolding & Architecture Compiler  
> 说明：本文描述**已实现并有测试覆盖**的机制。文中「实测」结论均来自可重复运行的自动化测试。

## 1. 要解决的问题

把《Universal 5D GemArc Web v5.0》这套提示词交给大模型时，模型每次都要重新发明同一批东西：
Canonical Model 的字段名、证据等级的说法、图的查询接口、Focus 退避的判定规则、
Building–Floor–Room 的归属语义、4D/5D 的仿真算法、工作流的语义约束。

结果是：每次产出都不一样，两次产出之间无法比较，改一个字段要重读三千行代码。

**本设计的做法是把「可被写死的东西」从模型手里拿走。** 模型只填事实，
固定件由 GemArc MCP 以脚手架的形式交付。

## 2. 三层固定件

```
固定件
├── 契约层  contracts/*.schema.json     ← 模型的数据长什么样
├── 词表层  vocab/*.json                ← 允许哪些词
└── 运行层  runtime/**/*.js             ← 引擎怎么工作
```

### 2.1 契约层

8 份 JSON Schema（draft 2020-12）：`canonical-model`、`node`、`edge`、`evidence`、
`space`、`view`、`scenario`（含 Case）、`workflow`。

模型填的每个对象都能对照 schema 检查，不需要模型记住字段名。

### 2.2 词表层

7 份词表，是**提示词、Python 校验器、浏览器运行时三方共用的唯一事实源**：

| 词表 | 内容 |
|---|---|
| `evidence-levels` | 6 级事实等级（Implemented / Observed / Designed / Inferred / Hypothetical / Unknown）+ 旧 4 级别名表 |
| `entity-kinds` | 21 种 Canonical 实体类型 |
| `edge-types` | 21 种关系类型，含方向、条件、权重、跨信任域标记 |
| `diagram-types` | 19 种图示类型，含各自的节点/关系白名单与保真要求 |
| `relation-classes` | 4 级相关性（Selected / Directly Related / Contextually Related / Unrelated）与对应视觉处理 |
| `space-levels` | Building / Floor / Room 的语义代表物与 8 种导航 |
| `case-categories` | 正常 / 异常 / 边界 / 组合 / 恢复 |

**为什么是唯一事实源**：Python 侧 `gemarc_mcp/model.py` 直接读取这些 JSON；
浏览器侧读取由同一份 JSON 生成的 `runtime/core/vocab-data.js`。
`tests/test_scaffold_vocab.py` 断言生成物与源文件一致，漂移会直接让测试失败。

> 早期版本里，Python 校验器用 4 级词汇、JS 校验器硬编码另一份集合，
> 导致 JS 拒绝了 Python 接受的模型。词表层就是为消除这类漂移而存在的。

### 2.3 运行层

浏览器侧的共用引擎，**零第三方依赖**（第三方库一律以工厂函数注入，缺省时用内置实现兜底）：

| 模块 | 内容 |
|---|---|
| `core/` | 稳定 ID、错误、模型归一化、词表访问 |
| `graph/` | GraphStore、GraphQueryEngine（15 个查询）、索引、持久化、交互、第三方适配器 |
| `focus/` | FocusContextEngine、RelevanceGraphEvaluator、RetreatAnimationController、ContextRestorationManager |
| `space/` | SpaceModel（Building–Floor–Room）、SpaceNavigation（8 种导航） |
| `sim/` | EventEngine、CausalEngine（与 `simulation.py` 同构） |
| `view/` | ViewState（跨视图同步）、ViewRouter（视图解析与保真缺失报告） |
| `workflow/` | WorkflowModel、WorkflowValidator、CanvasController |
| `interop/` | BPMN 2.0、UML XMI、ER、Draw.io 适配器 |

## 3. 归一化规则（Python 与 JS 双份实现，必须一致）

| 规则 | 旧写法 | 规范写法 |
|---|---|---|
| 边端点 | `source` / `target` | `sourceId` / `targetId` |
| 关系类型 | `kind` | `type` |
| 证据等级 | `confirmed` / `assumed` / `illustrative` / `unknown` | 6 级规范写法（大小写不敏感，旧写法作为别名接受） |

**实测**：`tests/test_model_compat.py` 覆盖 0.1.x 模型仍能加载、校验、归一化，
并断言归一化不修改入参。`tests/test_sim_consistency.py` 断言 Python 与 JS 的归一化结果一致。

## 4. 仿真内核：两端同构

4D/5D 仿真存在两份实现：Python（`simulation.py`，MCP 工具的权威）和 JavaScript
（浏览器侧，让动画真的由计算驱动，而不是回放预计算轨迹）。

**两份实现会漂移，所以有黄金用例。** `src/gemarc_mcp/scaffold/cases/simulation-golden.json`
保存 8 个场景的模型、干预与**逐字预期输出**：

| 用例 | 覆盖点 |
|---|---|
| linear / linear-blocked-middle / linear-blocked-source | 线性链、屏蔽中间、屏蔽源头 |
| tie-break | 同一毫秒的插入顺序 |
| fan-out / fan-out-blocked | 一事件触发多规则、分支屏蔽 |
| cycle-bounded | 因果环由 MAX_EVENTS 截断 |
| max-time | 越过 MAX_TIME_MS 截断 |

**实测**：`tests/test_sim_consistency.py` 用 `node runtime/tools/run-simulation.mjs`
跑同一批用例，要求 JS 输出与提交进仓库的预期**逐字相等**。任一端改动语义，这个测试立刻红。

## 5. 两种交付 profile，共用一份源码

站点外壳只有一份（`templates/shared/app.js`），两个 profile 只决定**模块怎么解析**：

| profile | 解析方式 | 依赖 | 启动 |
|---|---|---|---|
| `static` | import map：`@gemarc/runtime/` → `./runtime/` | 无（可选库走 CDN 或本地 vendor） | `python -m http.server` |
| `vite` | Vite alias：`@gemarc/runtime` → `runtime/` | npm 安装 three / graphology / dagre / dexie / sigma | `npm install && npm run dev` |

应用源码用与 profile 无关的裸标识符 `@gemarc/runtime/...` 导入，
因此**不会出现两份实现漂移**。

## 6. 脚手架的产出与填空流程

```
gemarc.scaffold demo --profile static
  → <workspace>/demo/
      model/architecture.json          ← 待填的槽位
      scaffold/
          contracts/  vocab/  runtime/   ← 固定件
          scaffold-manifest.json         ← 机读清单
          FILL-IN.md                    ← 人读的填空说明
```

`scaffold-manifest.json` 的 `slots` 列出每个槽位的 JSON Pointer、填什么、以及约束它的规则：

| 槽位 | 规则要点 |
|---|---|
| `meta.source` | 必须记录实际分析的分支与 Commit；仓库不可访问时不得伪造分析结果 |
| `nodes` | kind 取自 entity-kinds；verification 取自 evidence-levels；必须有稳定 ID、名称与证据 |
| `edges` | 端点必须存在；type 取自 edge-types；多条不同关系不得被错误合并 |
| `evidence` | 每条必须有可定位的 `source.locator`；无法定位时标 Unknown，而不是编造引用 |
| `space` | 每个容器必须写 `semanticSource`；虚拟房间不得冒充真实代码模块或物理部署设施 |
| `views` | diagramType 取自 diagram-types；保真要求无法满足时写进 `missing`，不要伪造 |
| `scenarios` / `cases` | evidenceClass 决定能否称为实际运行结果；Category 取自 case-categories |
| `workflows` | 条件流必须给出可被程序判断的 condition |

填完运行 `gemarc.build demo --profile static` 产出可发布站点。

## 7. 浏览器实测记录

> 记录日期：2026-10-25 ｜被测对象：`static` profile 产出的站点（`gemarc.build --profile static`）

站点以 `python -m http.server` 托管后，在真实浏览器中逐个标签页核对：

| 标签页 | 观察到的结果 |
|---|---|
| 1D 文字 | 系统资料与实体清单正常渲染；顶栏显示 `Hypothetical · 4 节点 / 3 关系` |
| 2D 图论 | 4 个节点与关系路径绘制成功 |
| 3D 空间 | Building–Floor–Room 语义与 `semanticSource` 如实展示，并显式声明未注入 legacy Viewer |
| 4D 动态 | 浏览器端真实计算产出 4 个事件：0ms / 10ms / 30ms / 40ms，traceId 与触发链正确，送达/阻断 = 4/0 |
| 5D 因果 | 屏蔽「消息队列」后，丢失事件为 `notify·send`、`queue·ingest`、`rule·evaluate` |
| 工作流 | 渲染正常，语义校验显示「通过」 |
| 控制台 | 零 error、零 warning |

**4D/5D 的浏览器输出与 Python 黄金用例 `linear` / `linear-blocked-middle` 逐字一致**，
这同时证明了「动画必须来自计算」和「两端同构」两条要求。

## 8. 边界与未完成项

- 3D 拾取仍需构建 legacy Viewer 后用 `--legacy-dist` 注入；`static` profile 本身不含 Three.js 渲染器。
- 工作流的深度语义校验在浏览器侧（`WorkflowValidator`），Python 侧只做结构性检查。
- 互操作适配器各有不可表达的部分（BPMN 表达不了 Evidence 等级，XMI 表达不了 Building–Floor–Room 等），
  逐项清单见 `runtime/interop/*.js` 的文件头。
- 浏览器核对覆盖了功能与控制台，**未做视觉回归**（没有像素级基线比对）；`gemarc.verify` 仍只做文件系统与 Schema 检查。
