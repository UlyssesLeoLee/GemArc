# 5D 脚手架与共用运行时设计

> 文档编号：BD-009 ｜版本：1.0 ｜日期：2026-10-25 ｜状态：已实现（Python 侧与浏览器侧均有自动化测试）  
> 产品：GemArc MCP — 5D Design Scaffolding & Architecture Compiler  
> 说明：本文描述**已实现并有测试覆盖**的机制。文中「实测」结论均来自可重复运行的自动化测试。

## 1. 要解决的问题

把《Universal 5D GemArc Web v5.0》这套提示词交给大模型时，模型每次都要重新发明同一批东西：
Canonical Model 的字段名、证据等级的说法、图的查询接口、Focus 退避的判定规则、
Building–Floor–Room 的归属语义、4D/5D 的仿真算法、工作流的语义约束。

结果是：每次产出都不一样，两次产出之间无法比较，改一个字段要重读三千行代码。

**本设计的做法是把「可被写死的东西」从模型手里拿走。** 模型只填事实，
固定件由 GemArc MCP 以脚手架的形式交付。

## 2. 三层固定件

```
固定件
├── 契约层  contracts/*.schema.json     ← 模型的数据长什么样
├── 词表层  vocab/*.json                ← 允许哪些词
└── 运行层  runtime/**/*.js             ← 引擎怎么工作
```

### 2.1 契约层

8 份 JSON Schema（draft 2020-12）：`canonical-model`、`node`、`edge`、`evidence`、
`space`、`view`、`scenario`（含 Case）、`workflow`。

模型填的每个对象都能对照 schema 检查，不需要模型记住字段名。

### 2.2 词表层

7 份词表，是**提示词、Python 校验器、浏览器运行时三方共用的唯一事实源**：

| 词表 | 内容 |
|---|---|
| `evidence-levels` | 6 级事实等级（Implemented / Observed / Designed / Inferred / Hypothetical / Unknown）+ 旧 4 级别名表 |
| `entity-kinds` | 21 种 Canonical 实体类型 |
| `edge-types` | 21 种关系类型，含方向、条件、权重、跨信任域标记 |
| `diagram-types` | 19 种图示类型，含各自的节点/关系白名单与保真要求 |
| `relation-classes` | 4 级相关性（Selected / Directly Related / Contextually Related / Unrelated）与对应视觉处理 |
| `space-levels` | Building / Floor / Room 的语义代表物与 8 种导航 |
| `case-categories` | 正常 / 异常 / 边界 / 组合 / 恢复 |

**为什么是唯一事实源**：Python 侧 `gemarc_mcp/model.py` 直接读取这些 JSON；
浏览器侧读取由同一份 JSON 生成的 `runtime/core/vocab-data.js`。
`tests/test_scaffold_vocab.py` 断言生成物与源文件一致，漂移会直接让测试失败。

> 早期版本里，Python 校验器用 4 级词汇、JS 校验器硬编码另一份集合，
> 导致 JS 拒绝了 Python 接受的模型。词表层就是为消除这类漂移而存在的。

### 2.3 运行层

浏览器侧的共用引擎，**零第三方依赖**（第三方库一律以工厂函数注入，缺省时用内置实现兜底）：

| 模块 | 内容 |
|---|---|
| `core/` | 稳定 ID、错误、模型归一化、词表访问 |
| `graph/` | GraphStore、GraphQueryEngine（15 个查询）、索引、持久化、交互、第三方适配器 |
| `focus/` | FocusContextEngine、RelevanceGraphEvaluator、RetreatAnimationController、ContextRestorationManager |
| `space/` | SpaceModel（Building–Floor–Room）、SpaceNavigation（8 种导航） |
| `sim/` | EventEngine、CausalEngine（与 `simulation.py` 同构） |
| `view/` | ViewState（跨视图同步）、ViewRouter（视图解析与保真缺失报告） |
| `workflow/` | WorkflowModel、WorkflowValidator、CanvasController |
| `interop/` | BPMN 2.0、UML XMI、ER、Draw.io 适配器 |

## 3. 归一化规则（Python 与 JS 双份实现，必须一致）

| 规则 | 旧写法 | 规范写法 |
|---|---|---|
| 边端点 | `source` / `target` | `sourceId` / `targetId` |
| 关系类型 | `kind` | `type` |
| 证据等级 | `confirmed` / `assumed` / `illustrative` / `unknown` | 6 级规范写法（大小写不敏感，旧写法作为别名接受） |

**实测**：`tests/test_model_compat.py` 覆盖 0.1.x 模型仍能加载、校验、归一化，
并断言归一化不修改入参。`tests/test_sim_consistency.py` 断言 Python 与 JS 的归一化结果一致。

## 4. 仿真内核：两端同构

4D/5D 仿真存在两份实现：Python（`simulation.py`，MCP 工具的权威）和 JavaScript
（浏览器侧，让动画真的由计算驱动，而不是回放预计算轨迹）。

**两份实现会漂移，所以有黄金用例。** `src/gemarc_mcp/scaffold/cases/simulation-golden.json`
保存 8 个场景的模型、干预与**逐字预期输出**：

| 用例 | 覆盖点 |
|---|---|
| linear / linear-blocked-middle / linear-blocked-source | 线性链、屏蔽中间、屏蔽源头 |
| tie-break | 同一毫秒的插入顺序 |
| fan-out / fan-out-blocked | 一事件触发多规则、分支屏蔽 |
| cycle-bounded | 因果环由 MAX_EVENTS 截断 |
| max-time | 越过 MAX_TIME_MS 截断 |

**实测**：`tests/test_sim_consistency.py` 用 `node runtime/tools/run-simulation.mjs`
跑同一批用例，要求 JS 输出与提交进仓库的预期**逐字相等**。任一端改动语义，这个测试立刻红。

## 5. 两种交付 profile，共用一份源码

站点外壳只有一份（`templates/shared/app.js`），两个 profile 只决定**模块怎么解析**：

| profile | 解析方式 | 依赖 | 启动 |
|---|---|---|---|
| `static` | import map：`@gemarc/runtime/` → `./runtime/` | 无（可选库走 CDN 或本地 vendor） | `python -m http.server` |
| `vite` | Vite alias：`@gemarc/runtime` → `runtime/` | npm 安装 three / graphology / dagre / dexie / sigma | `npm install && npm run dev` |

应用源码用与 profile 无关的裸标识符 `@gemarc/runtime/...` 导入，
因此**不会出现两份实现漂移**。

## 6. 脚手架的产出与填空流程

```
gemarc_scaffold demo --profile static
  → <workspace>/demo/
      model/architecture.json          ← 待填的槽位
      scaffold/
          contracts/  vocab/  runtime/   ← 固定件
          scaffold-manifest.json         ← 机读清单
          FILL-IN.md                    ← 人读的填空说明
```

`scaffold-manifest.json` 的 `slots` 列出每个槽位的 JSON Pointer、填什么、以及约束它的规则：

| 槽位 | 规则要点 |
|---|---|
| `meta.source` | 必须记录实际分析的分支与 Commit；仓库不可访问时不得伪造分析结果 |
| `nodes` | kind 取自 entity-kinds；verification 取自 evidence-levels；必须有稳定 ID、名称与证据 |
| `edges` | 端点必须存在；type 取自 edge-types；多条不同关系不得被错误合并 |
| `evidence` | 每条必须有可定位的 `source.locator`；无法定位时标 Unknown，而不是编造引用 |
| `space` | 每个容器必须写 `semanticSource`；虚拟房间不得冒充真实代码模块或物理部署设施 |
| `views` | diagramType 取自 diagram-types；保真要求无法满足时写进 `missing`，不要伪造 |
| `scenarios` / `cases` | evidenceClass 决定能否称为实际运行结果；Category 取自 case-categories |
| `workflows` | 条件流必须给出可被程序判断的 condition |

填完运行 `gemarc_build demo --profile static` 产出可发布站点。

## 6.1 工作指令由工具直接吐出

模型不必自己去读文件推导该做什么。新增 `gemarc_brief` 工具直接返回**精简工作指令**：

| 段 | 内容 |
|---|---|
| `purpose` | 这个 MCP 到底要达成什么 |
| `procedure` | 五步流程：读清单 → 读 schema 与词表 → 填槽位 → 严格校验 → 构建 |
| `rules` | 六条硬规则（事实不可臆造、等级不可混用、表现与执行分离、缺失如实标注……） |
| `slots` | 12 个槽位，每个带 JSON Pointer、填什么、约束规则 |
| `vocabulary` | 允许使用的全部词值：6 级证据、21 实体类型、21 关系类型、19 图示类型（含白名单与保真要求）、Case 分类、空间层级 |
| `commands` | 构建与启动命令 |
| `alreadyDone` | 固定件清单：哪些已经写好，模型不要重写 |

**实测**：整份 brief 约 10 KB，替掉原先 13323 字节的提示词规格，且信息全是可执行的
（槽位规则、词值白名单），而原规格的大部分篇幅在复述这些已存在的东西。

`gemarc-design` 提示词也已改为「先调用 `gemarc_brief` 取得精简工作指令与槽位清单，
不要自行发明字段名、证据等级说法或引擎」。

## 6.2 表现层与执行层分离（落到代码结构）

站点的表现逻辑抽到**纯 view-model 层** `templates/shared/view-model.js`：它把 Canonical Model
变成纯数据的节点树，不碰 DOM，因此可被单元测试与快照比对。`app.js` 只负责把数据树变成 DOM。

这同时解决了两个问题：

- **表现与执行分离**有了代码层面的落点：view-model 决定「怎么显示」，`runtime/sim` 决定「系统怎么跑」，
  两者不共享状态。
- **应用源码可以用 Node 直接测**。为此 runtime 改用**相对路径**导入（`./runtime/...`），
  而不是需要 import map / Vite alias 才能解析的裸标识符——应用在两个 profile 里都位于项目根目录，
  相对路径在浏览器、Vite 构建与纯 Node 三处都成立。

## 6.3 结构快照回归

`runtime/tools/dump-view-model.mjs` 把构建产物的各标签页 view-model 导出为 JSON，
`tests/test_view_model_structure.py` 与提交进仓库的基线逐字比对。

**实测**：该门禁在**构建产物**上运行（不是源码树），因此测的是真正交付的东西。
基线可用 `python -m gemarc_mcp.scaffold.viewmodel_baseline --write` 显式重生成。

> 这个门禁的价值在本次开发中被证实：浏览器复测发现 **2D 的边被节点方块完全遮盖**
> （矩形画在左边缘，连线却按「以该点为中心」计算，整条曲线落在方块下面），
> 而结构快照对这种「数值变了但测试仍通过」的缺陷无能为力——**只有真实渲染能发现它**。
> 两道门禁缺一不可。

## 6.4 3D 空间适配器（Three.js）

`runtime/space/space-viewer-three.js` 是第一个真实的三维渲染适配器。它**不硬依赖 three**：

```js
const renderer = createThreeSpaceRenderer(THREE, { container, model, space, store, onSelectNode, onSelectEdge, onHover });
```

`THREE` 由调用方注入——`static` profile 走 import map 指向 CDN，`vite` profile 走 `node_modules`，
测试则注入一个**行为对齐真实 three** 的桩（见下文）。

### 6.4.1 空间语义落到三维

| 层级 | 画法 |
|---|---|
| Building | 只画线框（一个包裹体量） |
| Floor | **唯一的实心板**，代表可站立的楼层 |
| Room | 只画线框，但**有垂直体量**：高度 = `floorHeight - floorThickness` |

房间不是楼板上的一片薄片，而是一个有高度的空间；节点站在房间地板上。
未分配到房间的节点落在 `y = 0` 的未分配区域内，不假装属于任何房间。
信任边界用虚线绘制，与普通关系在视觉上可区分。

### 6.4.2 拾取必须按屏幕像素度量

**世界半径不是目标大小**：同一条边在近处只有 1px、远处有 10px；细管在斜视角下几乎打不中。
这与 2D 用 14px 透明命中带是同一个问题的两种形态，因此 3D 同样采用屏幕空间容差：

| 目标 | 判定 | 容差 |
|---|---|---|
| 节点 | 射线命中（遮挡敏感）+ 屏幕距离 | `10px` |
| 关系 | 投影线段的屏幕距离 | `12px` |

- 节点与关系重叠时**节点胜出**，与 2D「节点画在上层」一致。
- 两条关系靠近时**最近者胜出**。
- 原先的「边拾取管」被移除：它让「射线命中的边」与「屏幕最近的边」互相打架。移除后边拾取是纯屏幕空间的。

### 6.4.3 取景：视锥精确贴合包围盒

早期实现用包围球半径算相机距离。工程空间通常**扁长**，球会把大半画布浪费在上下空白。
现由 `fitDistanceToBox()` 把包围盒的 8 个角点投影到相机自身坐标系上，逐轴求最大角点，
得出恰好贴合视锥的距离；`cameraForNavigation()` 额外接收 `fov` / `aspect` 上下文。

### 6.4.4 导航与错误码

`cameraForNavigation(id, context)` 覆盖词表定义的 8 个导航位置。
其中 `back-to-overview` 与 `overview` **参数完全相同**——这是「回到全局鸟瞰」的正确语义，
不是重复定义（模块注释已按此修正，行为不变）。

错误码：`GEMARC_SPACE_010`（无 WebGL）、`GEMARC_SPACE_011`（参数非法）。
WebGL 不可用时**显式降级并说明原因**，绝不用静态图或 2D 伪装三维。

### 6.4.5 测试：桩必须按真实 three 的方式工作

`runtime/tests/space-viewer.test.mjs` 共 27 项，桩在 `runtime/tests/helpers/three-stub.mjs`。
桩精确实现了 `Vector3` / `Quaternion` / `Object3D` 的矩阵语义，以及**射线-盒**、
**射线-开口圆柱**求交与 `Vector3.project`。

> 这条纪律是被迫学到的：three 的 `scale` 只作用于几何体，**不作用于自身位置**；
> 子节点世界位置 = 父世界位置 + 父世界缩放 ⊙ 子局部位置。
> 桩若早期错乘自身 scale，测出来的「边拾取管中心」就是歪的——**测试替身与真实客户端碰巧一致时，
> 通过的测试等于没测**。同理，three 相机沿 **-Z** 朝前看，世界射线方向必须由相机自身轴向量拼出。

## 6.5 MCP 功能微调控制台（主页）

远程端点的主角是 **MCP 本身**，不是某一份设计图。主页因此是一个**功能微调面板**：
列出服务器上真实注册的工具 → 在浏览器里改参数 → 直接调用 → 看真实返回。

### 6.5.1 控制台不发明能力

三条硬约束，都是从「固定件 + 共用代码」这条主线推出来的：

| 约束 | 做法 |
|---|---|
| 面板不许声称服务器没有的工具 | 工具列表、参数表单、输入契约全部来自 `tools/list` 的真实返回 |
| 写工具的名单不许在前端手抄一份 | `server.py` 的装饰器自带 `write=True` 标记，`/healthz` 下发该名单，页面据此上锁 |
| 路径不许写死 | 服务端渲染时注入 `mcpPath` / `healthPath` / `sitePath` / `writeTools` |

写工具被选中时，参数表单照常渲染（方便看清参数契约），但调用按钮显示「写工具已关闭」并禁用——
**面板把服务端的安全边界如实呈现出来，而不是替它假设**。

### 6.5.2 浏览器直连 MCP

面板不走任何后端桥接，直接对 `/mcp` 发 JSON-RPC。之所以可行，是因为端点用的是
**无状态模式**（`stateless_http=True` + `json_response=True`）：一次 POST 换一次 JSON 响应，
不需要 session id，因此**同源、无 CORS**。

### 6.5.3 设计图不丢，只是换了位置

脚手架产出的 5D 站（含 3D 适配器）仍从包内源码物化（首次访问 `/site/` 时才构建），挂在 `/site/`。
主页是控制台，`/site/` 是产物——两者角色不同，不该混为一页。

## 7. 浏览器实测记录

> 记录日期：2026-10-25 ｜被测对象：`static` profile 产出的站点（`gemarc_build --profile static`）
>
> 3D 标签页使用一份独立的演示模型（2 楼宇 / 4 楼层 / 5 房间 + 1 未分配区域 / 8 节点 / 5 关系），
> `gemarc_validate` 结果为 0 error、0 warning。

站点以 `python -m http.server` 托管后，在真实浏览器中逐个标签页核对：

| 标签页 | 观察到的结果 |
|---|---|
| 1D 文字 | 系统资料与实体清单正常渲染；顶栏显示 `Hypothetical · 4 节点 / 3 关系` |
| 2D 图论 | 4 个节点与 3 条关系绘制成功；边的独立拾取区域可点击，选中的是**边**（RELATION / e2 / queue→rule）而非源节点 |
| 3D 空间 | **真实 WebGL 渲染**：主系统 3 层楼板 + 边缘站点 + 未分配节点区域 + 信任边界虚线全部可见；悬停命中节点（消息队列）与关系（边缘上报 e5）；点击节点选中节点、点击关系选中**关系**而非源节点；inspector 随之切换，切到 2D 标签页后选中态保持一致 |

| 5D 因果 | 屏蔽「消息队列」后，丢失事件为 `notify·send`、`queue·ingest`、`rule·evaluate` |
| 工作流 | 渲染正常，语义校验显示「通过」 |
| 控制台 | 零 error、零 warning |

**4D/5D 的浏览器输出与 Python 黄金用例 `linear` / `linear-blocked-middle` 逐字一致**，
这同时证明了「动画必须来自计算」和「两端同构」两条要求。

## 8. 边界与未完成项

- 工作流的深度语义校验在浏览器侧（`WorkflowValidator`），Python 侧只做结构性检查。
- 互操作适配器各有不可表达的部分（BPMN 表达不了 Evidence 等级，XMI 表达不了 Building–Floor–Room 等），
  逐项清单见 `runtime/interop/*.js` 的文件头。
- 回归护住的是**呈现结构**（view-model 快照），不是像素；`gemarc_verify` 仍只做文件系统与 Schema 检查。
- **提交进仓库的生成物必须与生成它的代码同步**。随附预览站 `examples/demo-site` 曾因模型字段
  改名而停留在旧口径，浏览器实测显示它**画出 4 个节点、0 条关系**，而仓库里所有测试都是绿的。
  现在 `tests/test_generated_artifacts.py` 用真实构建路径重新生成一份并逐字节比对；
  远程端点则改为**首次访问 `/site/` 时从包内源码物化站点**（懒构建），从根上消除「快照漂移」这一类问题。
