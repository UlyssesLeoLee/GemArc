# 6D 执行图与工作分解设计（WBS × 执行图）

> 文档编号：BD-011 ｜版本：1.0 ｜日期：2026-11-04 ｜状态：设计基线（本次已随代码落地）
> 产品：GemArc MCP — 多媒体文档脚手架
> 关系：本文是 6D 维度的定义与验收细则。ADR-014 定义了 6D 执行图层（怎么跑），ADR-015 把 6D 的定义补全为「WBS × 执行图」；两者冲突时以本文为准。

## 1. 立意：6D 回答的是「这次要交付什么，怎么交付」

前五个维度各回答一个问题：1D 是事实，2D 是结构，3D 是空间与语义，4D 是时间，5D 是因果。**6D 回答的是第六个问题：这份文档背后的工作，要怎么被拆开、被执行、被交付。**

这个问题的答案有两半，缺一不可：

- **执行图（Execution Graph）**：谁来做、做成什么样、失败了怎么办。节点承担具体能力（Agent 循环、确定性程序、人工审批、工具调用、策略闸门、检查点），边规定路由与依赖，结构化状态沿边传递并在关键边界持久化。
- **WBS（工作分解）**：这次工作分成哪几块，每块**交付什么**、**什么时候算完成**。阶段 → 工作包 → 任务，每一层都有交付物与完成条件。

只做执行图，6D 就只能回答「怎么跑」，回答不了「交付什么、做到哪一步算完」；只做 WBS，就只剩一张甘特图，没有执行语义。**6D 是两者的乘积：WBS 说做什么，执行图说怎么做，两者靠绑定关系连起来。**

## 2. 概念来源与取舍

2026 年 7 月起，业界用 **Graph Engineering** 描述这一层（参考：`00_管理/03_引用标准及适用声明.md` 第 6 条）。它的核心主张与本文一致：

- **工作图（work graph）**：一次任务如何完成。节点是分析、实现、测试、审批或工具调用；边表示依赖、分支、回流与状态传递。
- **改进图（improvement graph）**：系统如何长期调整。节点是指标、评估、策略、审计与人工决策。

**取舍**：GemArc 的 6D 只做工作图。改进图是系统自我优化的层，与本产品「交付可审查文档」的职责不是一回事，本轮明确不做。

Graph Engineering 的另外三条主张也一并采纳：

| 主张 | GemArc 的落法 |
|---|---|
| Loop 是图中的基本执行单元 | `agent-loop` 是执行节点种类之一，必须声明 `iterationLimit` 与 `budgetPolicy` |
| 图不限于 DAG：需要条件分支、驳回、重试、暂停、恢复的回边 | 执行边种类含 `conditional-flow` / `error-flow` / `retry-transition` / `resume-transition` / `approval-transition` |
| 状态是可交接的事实，不是对话记录 | 状态契约版本化、检查点边界、幂等键、治理点都在执行图契约里 |

## 3. WBS 层：交付物与完成条件是定义要素

工作包是 6D 里的新对象，住在执行图里：`executionGraph.workPackages[]`。

| 字段 | 含义 | 规则 |
|---|---|---|
| `packageId` | 稳定 ID | 必填 |
| `parentPackageId` | 父包 | 顶层阶段为 `null`；树有且只有一个根，不得成环 |
| `kind` | `phase` / `work-package` / `task` | 三级 |
| `title` | 标题 | — |
| `deliverable` | **交付物**：这一层产出什么 | 必填 |
| `completionCriteria` | **完成条件**：何时算做完 | 必填 |
| `nodeIds` | 归属的执行节点 | 叶子包必填且非空 |
| `dependsOn` | 跨包依赖 | 依赖与执行边是两件事，不得互相替代 |

两条硬规矩：

1. **没有交付物与完成条件的包不构成 WBS。** 一句「做调研」不是工作包；「产出带来源的现状清单，每条结论都能指回来源」才是。
2. **层级节点只做汇总。** 阶段与工作包可以只挂子包；真正承载执行的是叶子任务与它的执行节点。

## 4. 融合规则：两半必须对得上

| 规则 | 判据 | 命中时的门 |
|---|---|---|
| 执行节点必须归属至少一个工作包 | 执行节点不在任何 `nodeIds` 里 | `wbs_orphan_node`（`GEMARC_EXEC_009`） |
| 工作包树必须完整且绑定不断 | 多根/无根、父包不存在、成环、ID 重复、引用了不存在的节点 | `wbs_broken_hierarchy`（`GEMARC_EXEC_010`） |
| 每个包必须有交付物与完成条件 | `deliverable` 或 `completionCriteria` 为空 | `wbs_missing_deliverable`（`GEMARC_EXEC_011`） |
| 叶子包必须绑定执行节点 | 叶子包 `nodeIds` 为空 | `wbs_unbound_package`（`GEMARC_EXEC_012`） |

派生层据此给出**覆盖率**：`assignedNodeCount / nodeCount`。覆盖率为 1 表示分解与执行完全对上；有执行节点没被任何包覆盖，就是分解漏了工作。

**执行节点只有一套口径。** 执行节点 = 工作流画布上承担执行能力的节点 ∪ 执行图契约自带的节点，认定依据是节点种类（9 种 6D 执行种类）与执行字段（13 项）。站点卡片上的「执行节点归属 X / Y」必须与 `workflow-ir.json` 的 `wbs` 用同一条判定：同一个模型在卡片上和在产物里只能有一个分母，否则「覆盖率 1」这句话就没有唯一含义。

**这四条门只对声明了工作分解的工作流生效。** 没有 WBS 的 6D 工作流照旧按原有 8 条门判定；纯 5D 画布不受约束。增量原则与 ADR-013/014 一致。

## 5. 反面清单（不得做的事）

- 不得把「工作包」当成节点的重命名：包有交付物与完成条件，节点有执行器与契约。
- 不得用一个工作包吞掉整棵执行图来「假装有 WBS」——那只是把图换了名字。
- 不得让执行边代替包依赖：边是运行时路由，`dependsOn` 是工作顺序。
- 不得为没有交付物的层编造交付物；缺了就写「未提供」。
- 不得在层级包里硬塞节点来绕过「叶子包必须有节点」的判定。
- 不得让站点与派生产物各算一套执行节点口径（分母不同则覆盖率不可比）。
- 不得把改进图（指标 / 策略 / 审计构成的长期调整层）混进本轮 6D。

## 6. 验收口径（可测）

| 验收项 | 怎么判 |
|---|---|
| WBS 三级与字段目录已发布 | `scaffold/vocab/workflow-kinds.json` 的 `workPackageKinds` / `workPackageFields` / `wbsContract` |
| 契约能表达工作分解 | `execution-graph.schema.json` 有 `workPackages`；示例文件自证一棵三层分解 |
| 门会拒绝坏的分解 | 四条门各有用例，且错误码是 `GEMARC_EXEC_009`…`012` |
| 派生给出树与覆盖率 | `workflow-ir.json` 的 `workPackages` / `wbs` |
| 站点读得到 | `static` / `vite` 的工作流视图渲染 WBS 树；`mvp` 预览有「工作流」标签页 |
| 没有 WBS 就不受影响 | 未声明工作分解的 6D 工作流仍然零新增门 |
