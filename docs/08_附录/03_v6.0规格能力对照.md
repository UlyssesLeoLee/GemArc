### 2.1 6D 的定义补全：WBS × 执行图（ADR-015 / BD-011）

规格把 6D 写成「执行图」，只覆盖了**怎么跑**。2026 年 7 月起业界用 Graph Engineering 描述这一层，它把图分为工作图（一次任务如何完成）与改进图（系统如何长期调整）；工作图仍只讲怎么跑，不讲**做什么工作、分解到哪一级、交付什么**——那是 WBS 的职责。因此本仓库把 6D 的定义补全为两者的乘积：

| 层 | 回答什么 | 落点 |
|---|---|---|
| WBS 分解层 | 做什么、交付什么、何时算完成 | `executionGraph.workPackages[]`：`kind` 三级（`phase` / `work-package` / `task`）、`deliverable`、`completionCriteria`、`nodeIds`、`dependsOn` |
| 执行图层 | 谁来做、怎么路由、状态怎么交接 | 既有的执行节点 / 边 / 运行 / 检查点契约（§25–§28） |

配套增量（全部可选增量，与 ADR-013/ADR-014 一致）：

- 词表：`workflow-kinds` 增 `workPackageKinds` / `workPackageFields` / `wbsContract`；`qualityGates.rejectOn` 由 8 条增至 12 条。
- 契约：`execution-graph.schema.json` 增 `workPackages`；示例文件增一棵三层分解。
- 派生：`data/workflow-ir.json` 增 `workPackages`（含 `childPackageIds` / `nodeCount`）与 `wbs`（`rootPackageId` / `coverageRatio` / `kinds`）。
- 站点：`static` / `vite` 的工作流视图渲染 WBS 树；`mvp` 预览新增「工作流 / WBS + Execution」标签页。
- **口径**：执行节点 = 画布执行节点 ∪ 执行图契约自带节点（9 种 6D 执行节点种类 + 13 个执行字段）；站点列表、覆盖率与 `workflow-ir.json` 的 `wbs` 同口径，一个模型只有一个分母。
- **发布示例**：示例模型带 6D 工作分解（一棵三层 WBS），`gemarc_render` 仍全内联（内联上限 24 → 35 KiB；实测响应 11,732 token，见 `docs/02_基本设计/11_6D执行图与工作分解设计.md` §6.1）。
- **不在范围内**：Graph Engineering 的改进图（指标 / 评估 / 策略 / 审计构成的长期调整层）。GemArc 的 6D 仍然只做工作图。

## 4. 「能妥善实现」的可核对口径

| 主张 | 怎么核对 | 现状 |
|---|---|---|
| 模型能表达规格逐条列出的每个字段与枚举 | `tests/test_v5_spec_coverage.py`：把规格里的字段与枚举原样抄进断言 | 71 项覆盖测试，覆盖 §4 / §10 / §14 / §15 / §18 / §25 / §26 / §33 |
| 规格拼写与正本拼写都能用 | 同文件的 `AliasTests` | `type`/`label`/`direction`/`nodeType`/`edgeType`/`guard`/`portId`/`caseId` 等别名被接受并归一 |
| 派生文件与模型一致 | 同文件的 `DerivedFileTests` | 证据索引的反向引用、图示缺失项、空间落位、GWF-IR 字段名、Case 契约逐项对拍 |
| 判定结果与渲染结果一致 | 同文件的 `RuntimeParityTests` | 同一份语料交给 Python 与浏览器运行时各判一次，别名归一与保真判定必须逐条相同 |
| 6D 质量门会真的拦住坏模型 | 同文件的 `ExecutionGateTests` | 8 条门各有正反例：声明执行图且违规时报错，纯 5D 画布不报 |
| 渲染与本地构建逐字节一致 | `tests/test_stateless.py` 的 `test_render_plus_kit_equals_build_byte_for_byte` | kit + `gemarc_render` 的文件 == `gemarc_build` 产出的文件 |
| 缺失信息被标为缺失而非伪造 | `diagram-catalog.json` / `spatial-layout.json` / `workflow-ir.json` 的 `missing` 与 `issues` 字段 | 保真元素探测表与运行时同源；未登记的 token 一律记为缺失 |
| 文档里的数字不是抄来的 | 同文件的 `DocumentBindingTests` | 本文引用的词表规模与覆盖测试数量由测试当场读出并核对 |

## 5. 固定件站点外壳的 UI/UX 基线

固定件（kit）自带的站点外壳按「多媒体文档」的要求实现下列基线，使用方不需要改固定件就能得到这些行为：

| 要求 | 外壳里的实现 |
|---|---|
| 主要显示内容突出、占比大 | 主栏为主内容区（`1fr`），结构图/时间轴/工作流图是首屏主体；顶栏「专注」开关把两侧窗格收成一条窄导航条，主内容占满窗口 |
| 窗格可调宽度 | 侧栏与检查器之间各有一条可拖拽分隔条，宽度写入浏览器本地存储；双击分隔条复位；方向键可微调 |
| 主内容区不会被挤小 | 主栏有最小宽度下限，侧栏与检查器各有最小宽度；拖到极限也不会把主栏压到不可用 |
| 窗格可调高度 | 内容面板（卡片）右下角有拖拽手柄，可单独调整每个面板的宽与高 |
| 导航不丢 | 专注模式只收窄侧栏，不移除它：页签始终可达 |
| 无障碍 | 分隔条是 `role="separator"`，可聚焦、可键盘操作，可访问名里带着当前宽度 |

> 服务器随包发布的那份流程正文把「一轮 UI/UX 优化」列为**硬规则**：制作多媒体文档时必须做这一轮复核，并把结果写进最终说明。能力由固定件提供，事实由模型提供。
>
> 上述行为已在真实浏览器里逐项实测（拖拽分隔条、专注开关、刷新后尺寸保留、页签切换）。

## 6. 明确不做的事

- **不由 MCP 生成的**：三维宝石几何与材质、无限画布交互、原型标签页、浏览器端持久化、适配器的完整实现、AI Patch 引擎、真实浏览器验收。这些是目标工程的实现责任；MCP 只保证它们所依赖的语义契约是完整且可机读的。
- **不由 MCP 执行的**：真实执行器、检查点持久化、审批界面、审计流水。6D 契约只约束「可以这样声明」与「不可以这样声明」，不代替执行。
- **不由 MCP 判定的**：因果识别（§16 的干预比较是规则化 what-if，不证明真实世界的因果关系）、证据等级的真假（事实由证据决定，MCP 只校验一致性）。
- **不承诺的**：交互质量、性能指标、浏览器兼容性——这些需要目标工程的真实浏览器验证。
