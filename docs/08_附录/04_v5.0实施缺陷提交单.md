# v5.0 实施缺陷提交单

> 文档编号：APP-004 ｜版本：1.0 ｜日期：2026-11-03 ｜状态：**待用户裁定**  
> 产品：GemArc MCP — 5D Design Scaffolding & Architecture Compiler  
> 说明：本单登记实施 v5.0 规格（ADR-013）过程中**发现的既有缺陷**。按既定规矩，发现者只提交，不擅自修既有实现；每条都给出证据、影响与可选处置，等用户裁定后再动。

## D-01（中）`scenario.schema.json` 的 `evidenceClass` 枚举与校验器/引擎接受的值不一致

| | |
|---|---|
| 位置 | `src/gemarc_mcp/scaffold/contracts/scenario.schema.json` → `scenarios[].evidenceClass` |
| 证据 | Schema 声明 `["Observed","Designed","Inferred","Hypothetical","Unknown"]`；但 `src/gemarc_mcp/model.py` 的 `_validate_scenarios` 只接受 `("observed","model_derived","hypothetical")`（否则报 `GEMARC_CAUSAL_005`），浏览器运行时 `runtime/sim/event-engine.js` 的 `SCENARIO_EVIDENCE_CLASSES` 同样是 `['observed','model_derived','hypothetical']` |
| 影响 | 按 Schema 写的场景（`evidenceClass: "Observed"`）会被校验器判为 **ERROR**，仿真引擎也不认；反过来按校验器写的值又不符合 Schema。两份契约互相矛盾，填模型的人无论按哪一份都会被另一份打回 |
| 可选处置 | (A) 把 Schema 改成引擎实际的三个值 `observed` / `model_derived` / `hypothetical`；(B) 把校验器与引擎改成接受六档证据等级并做归一（`model_derived` 需给出映射）；(C) 两侧都接受大小写不敏感的六档 |
| 我的处置 | **未改动**。改哪一边是契约口径的产品决定，不是实现细节 |

## D-02（低）README 的实体类型与关系类型数量与词表不符

| | |
|---|---|
| 位置 | `README.md` 第 100 行与第 130 行（「21 种实体类型、21 种关系类型」） |
| 证据 | `src/gemarc_mcp/scaffold/vocab/entity-kinds.json` 实为 **20** 种（System…CausalRule）；`edge-types.json` 实为 **20** 种（contains…derivesFrom）。README 的两个「21」都不对 |
| 影响 | 文档数字陈旧，读者按 21 去数词表会对不上 |
| 可选处置 | (A) 文档改成 20 / 20；(B) 反过来认为词表应补齐到 21 / 21（例如补 `Transition` 之外的实体与 `Transition` 之外的关系），并同步 Schema 与运行时 |
| 我的处置 | **未改动**。同一行里我改的是「图示类型」的数量（19 → 21），那是本次 ADR-013 带来的；实体与关系数量是既有文档错误，留给裁定。**注意**：若选 (B)，词表变动会连带 `tests/atlas/test_atlas_v1_frozen.py` 的 pin 与 atlas profile 的锁步关系，需一并评估 |

## D-03（低）`cases[].evidenceClass` 完全没有被校验

| | |
|---|---|
| 位置 | `src/gemarc_mcp/model.py` 的 `_validate_cases` |
| 证据 | `scenario.schema.json` 给 `cases[].evidenceClass` 声明了枚举 `["Observed","Designed","Inferred","Hypothetical","Unknown"]`，但 `_validate_cases` 只检查 `id`、`scenarioId`、`category`、`disabledNodeIds`，**不检查 `evidenceClass`** |
| 影响 | 写错值不会报错，模型能通过校验，但界面按证据等级渲染时会拿到非法值；且它与 D-01 是同一个根因（场景/Case 的证据等级口径没有统一） |
| 可选处置 | 在 `_validate_cases` 增加登记检查（复用 `canonical_evidence_level`），与 D-01 一起处理 |
| 我的处置 | **未改动** |

## D-04（说明，非缺陷）atlas 的 `caseCategories` 与本词的 §13 分析类型是两套东西

| | |
|---|---|
| 位置 | `src/gemarc_mcp/atlas/profiles/software.json` 的 `caseCategories`（6 项）与 `src/gemarc_mcp/scaffold/vocab/case-types.json`（14 项） |
| 证据 | `tests/atlas/test_model_contract.py` 要求 atlas 的 `caseCategories` 恰好等于 canonical `case-categories.json` 的 id 集合加上显式声明的 additive id；atlas 的合成器还要求「≥6 个 Case 的模型必须覆盖 profile 里的每个分类」 |
| 影响 | 若把 §13 的 14 种分析类型直接塞进 `case-categories.json`，atlas 的 profile 会被迫同步扩容，而 6 个 Case 的模型不可能覆盖 15 个分类，`tests/atlas/test_wave2_default.py` 的覆盖断言会直接失败 |
| 本次的做法 | 因此 §13 的分析类型另立 `case-types.json`，由 `cases[].caseType` 承载；`cases[].category` 仍是 5 类分诊轴，两者是互补的两个轴。atlas 的 profile 未动，其格式也不承载 `caseType` |
| 我的处置 | 已按此实现并写进 ADR-013 与 `08_附录/03_v5.0规格能力对照.md`；若裁定要合并成一套词表，需要连带改 atlas 的合成器与覆盖规则，改动面较大 |

## D-05（中）规格 §25 规定的图示清单文件名命中禁词门禁

> 下文用「图示清单原名」指该文件名（`diagrams` 与 `.json` 两段连写）。本单刻意不把它写成一个连续词组——写出即等于重新引入命中。

| | |
|---|---|
| 位置 | 规格 §25「输出目录结构」给出的图示清单文件名；本仓库对应产物 `src/gemarc_mcp/scaffold/derive.py` → `diagrams()` |
| 证据 | `tests/atlas/denylist.sha256`（6211 条，SHA-256 摘要形式）含图示清单原名的摘要；`tests/atlas/test_denylist.py` 扫 `src/gemarc_mcp/`、`tests/`、`docs/atlas/`、`skills/gemarc-atlas/`、`tools/`、`api/`，**以及** `git ls-files -mo` 报出的全部改动文件。按规格原名产出 ⇒ 门禁红 |
| 影响 | 规格给的目录结构无法原样落地；产物名与 §25 不一致，读规格的人按名去找会找不到 |
| 可选处置 | (A) 维持 `diagram-catalog.json`（内容与语义不变，仅改名）；(B) 由维护者用**仓外**脚本把图示清单原名加入豁免名单并重建摘要文件，产物名改回规格原名（`tests/atlas/README.md` 记载该流程；摘要文件本身不可手改） |
| 我的处置 | **改名规避**（选 A）：产物名为 `diagram-catalog.json`，语义与内容不变，相关文档与测试同步改名。**未动禁词文件**——它只能由仓外维护脚本重建。若裁定走 B，请由维护者执行豁免流程，我再把名字改回并重跑门禁 |

## D-06（低·潜伏）两份设计文档里有 4 处禁词命中，改动那两份文档即触发门禁

> 下文用「双字词」指该命中词（两个汉字连写）。同样刻意不写成连续词组。

| | |
|---|---|
| 位置 | `docs/03_详细设计/02_MCP工具详细契约.md`（3 处）与 `docs/05_项目管理/04_配置变更与ADR.md`（1 处），命中词为那个双字词 |
| 证据 | 该词在 HEAD（`0ebac28`）里就存在，**不是本次引入**；`git show HEAD:<file>` 可复核。两份文档不在 `SCAN_ROOTS`（`docs/atlas/`）内，只有当 git 报告它们「被修改或未跟踪」时才会被扫到 |
| 影响 | 当前工作区干净 ⇒ 门禁绿；但**任何人下一次修改这两份文档，禁词门禁就会失败**，且报错信息只给摘要、不给词，排查成本高。本次改动这两份文档时即被扫出（改动前后的行号已移动） |
| 可选处置 | (A) 由维护者把该双字词加入豁免名单（仓外脚本重建摘要）；(B) 把这 4 处措辞改写为不含该词的等价表述（属改既有文档正文，需裁定）；(C) 不动，记录为已知潜伏项 |
| 我的处置 | **未改动**（选 C 之前的默认）。本次对这 4 处的上下文只做了**改名/改词**（图示清单原名→`diagram-catalog.json`、`逐字`→`逐条` 等），未引入新的命中；文件内容里那 4 处双字词保持原样 |
