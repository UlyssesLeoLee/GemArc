## V-01（中）模型里出现一条双向依赖，2D 视图会整张塌成一条横带，而校验器不报

| | |
|---|---|
| 位置 | 布局：`src/gemarc_mcp/scaffold/templates/shared/view-model.js` 的 `layeredLayout()`（`:94`–`:121`，秩的计算在 `:97`–`:107`，坐标在 `:117`）<br>校验：`src/gemarc_mcp/model.py`（全文**没有**任何环检测规则） |
| 根因 | `layeredLayout` 用「最长路径分层」给节点排秩：从每条边 `source → target` 递推 `rank(target) = max(rank(target), rank(source) + 1)`，并用 `Math.min(nodes.length - 1, …)`（`:100`）把秩**夹在上限内**。这套算法**只在有向无环图上成立**：一旦模型里出现环，环上的秩会每轮再涨一格，直到被夹到上限。于是「层」被撑到最大，SVG 的 `viewBox` 宽度（`width = 90 + rank * 240 + 200`）暴涨，而节点最多的那一列只有几行——整张图被等比压扁，节点文字互相重叠，整幅图**不可读** |
| 证据 | 见下方「实测原始数据」 |
| 后果 | **模型侧完全无感**：改动前后 `gemarc_validate` 都是 **0 error 0 warning**，`strict=true` 也是 0/0；`gemarc_build` 成功且自带校验 0/0；`gemarc_verify` 通过（它只查文件完整性与结构，`check=filesystem_and_schema_only`）。构建还会写一句「4D/5D 是显式规则模拟 MVP；未进行真实浏览器/WebGL 测试」——**没有任何一处提示「这个模型画出来会糊」** |
| 影响 | ① 凡是模型里存在**互为依赖**的一对节点（很常见：例如「令牌」与「签发令牌的动作」、「服务」与「调用服务的动作」），2D 视图就不可读，而交付物本身看起来一切正常；② 这个缺陷**只有真正渲染一次才能发现**，所以它会一路活到交付那一刻；③ 对 `gemarc_render` 这条远程路径，调用方拿到的是「9 个数据文件 + 校验通过」，完全无从判断 2D 视图能不能看 |
| 可选处置 | (A) **校验器报出来**：在 `model.py` 加一条环检测（有向图找强连通分量），命中就报 ERROR 并点名环上的节点。模型于是「不合格」，作者必须改成单向依赖或另立一条关系——**失败得响**；(B) **布局能画环**：在 `layeredLayout` 里先破环（例如把强连通分量压成一列，或在去环后的副本上排秩），模型可以有环，图仍然可读；(C) **(A) + (B)**：环是模型层的问题，报出来；视图层也不该因此崩掉，两边都做；(D) **最轻的一层保险**：视图侧加阈值保护——算出来的 `viewBox` 宽度超过某个倍数就换一种布局，而不是等比压到看不清 |
| 需要你拍板的前提 | **「模型里允许不允许出现环」这件事本身还没定**。词表 `workflow-kinds.json` 的 `rules` 与 `validity` 只要求「不得声称可执行」「不得伪称」，没有一条禁止节点之间成环；`docs/atlas/spec/` 下也没有环检测的约定。所以 (A) 属于**新增一条模型级规则**，要走设计文档；(B)/(D) 属于视图实现改动 |
| 我的处置 | **未改**（(A)–(D) 都要你裁定；而且 (A) 要先改设计文档）。本单只附证据 |

## 实测原始数据

模型：41 节点 / 72 边（改动前），唯一的一处环是这两个节点互为依赖：

```
e43  令牌签发            -> 个人访问令牌（PAT）   kind=triggers    ev=ev-accounts-token-post
e44  个人访问令牌（PAT）  -> 令牌签发             kind=publishes   ev=ev-pat
```

按 `layeredLayout` 的算法复算：

```
nodes 41   edges 72   秩松弛迭代 21 轮后收敛
秩分布：rank 0:5  1:4  2:4  3:1  4:1  5:2  6:8  7:6  8:4  9:2  40:4
秩 = 40 的 4 个节点：个人访问令牌（PAT）/ api_tokens / audit_log / 令牌签发
```

`40` 就是 `Math.min(nodes.length - 1, …)` 的夹取上限（41 − 1 = 40）。于是：

```
SVG viewBox 宽度 = 90 + 40 * 240 + 200 = 9890 px
最高的一列只有 8 个节点 -> viewBox 高度 ≈ 70 + 7 * 92 + 90 = 804 px
```

`9890 × 804` 的画布塞进约 1010 px 宽的面板 ⇒ 缩放约 **10%**，节点框从 148 px 缩到约 15 px，标签互相叠在一起，整幅图只剩一条横带（浏览器与无头浏览器两种环境都一样）。

把这条冗余的回边去掉之后（72 边 → 71 边，其余不变），同一个模型、同一套工具、同一套校验：

```
gemarc_validate（strict=true）-> 0 error 0 warning，modelSha256=95ecfeed…
gemarc_build                  -> ok，validation 0 error 0 warning
gemarc_verify                 -> ok
2D 视图                        -> 41 节点 / 71 关系，标准分层图，节点与边都读得清
```

## 复现方式

1. 造一个含环的模型（让 A 与 B 互为依赖），或直接用上面这两个节点与两条边；

3. `gemarc_scaffold` + 写入模型 + `gemarc_build` → 成功，校验 0/0；

## 顺带核实的部分（**没有**问题）

- 秩的递推本身是**确定性的**：同一模型永远同样的布局，符合 `view-model.js:93` 注释里「同一模型永远长得一样」的说法；
- 环**不会**让构建失败、不会让校验报错、也不会写出半截文件——它只是让图不好看。也就是说这个缺陷**没有任何自愈或兜底**；
- 节点多于边、或边连到视图之外的节点，都不会触发同样的塌陷：布局只用视图内的节点与边（`view-model.js:139` 调用处与 `:96` 的过滤），这条路径是干净的；
- 除 2D 之外的维度（1D 清单、4D/5D 事件流、6D 工作流）在本模型上都渲染正常，没有同类问题。
