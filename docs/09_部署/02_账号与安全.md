**运行时的几个边界（如实写出）**：

- 账号路由只认 `GEMARC_ACCOUNTS_BASE_URL` 里的**那一个主机名**：请求用别的主机名（Vercel 预览地址、`*.vercel.app` 部署地址、`www.` 别名）会得到 421 `GEMARC_ACCT_001`。
  请把基址设成生产别名，并**只在生产别名上**测试登录。（`/mcp` 与 `/healthz` 的路径判断是既有的 `endswith` 规则，先于账号路径，这一点不是本功能引入的。）
- 没有可信客户端 IP 时（不在 Vercel 上且没设 `GEMARC_ACCOUNTS_TRUSTED_PROXY_HOPS`，或 Vercel 上缺 `x-vercel-forwarded-for`），**按 IP 的数据库限额（`login_start`、`login_callback`、`signup_ip`）不生效**；
  进程内预过滤改用「连接地址 + `User-Agent` + `Accept`」的短哈希做键（不再是全员共享的一个桶）。这只是负载保护，不是安全边界。配置检查在这种情形下给出 `no_trusted_client_ip` 警告（启动日志与 `doctor`/`status`）。
- 注册限额的检查顺序是**先按 IP、后全局**，只有通过 IP 检查的尝试才消耗全局额度。分布式来源（很多 IP）仍可耗尽全局 60/小时，这是残余风险 R7。
- `GEMARC_ACCOUNTS_MAX_USERS` 数的是**所有**用户行（含已停用的）。在 Postgres 上上限检查与插入由 `pg_advisory_xact_lock` 串行化（**未对真实 Postgres 验证**）；SQLite 由 `BEGIN IMMEDIATE` 串行化。

## 0. 范围、前提与不变量

### 0.0 需要你确认的两件事（评审后新增）

> 这两件事决定你最终拿到的东西。请在实现开始前确认；没有回复时，实现按本文的默认值进行。

1. **「登录」落在 MCP 客户端那一侧，等于「粘贴一个个人访问令牌（PAT）」。** 你要的是 Gmail 注册登录；本期交付的是：浏览器里 **Google 登录** → 在账号页创建 PAT → Claude Code / Codex / Hermes 把 PAT 写进配置，以 `Authorization: Bearer` 调 `/mcp`。**代价**：客户端配置里躺着一个长寿命的凭据（默认 30 天、默认上限 90 天）；claude.ai 自定义连接器**用不了** PAT。**替代方案**：实现 MCP 授权规范（OAuth 2.1）——支持它的客户端会直接弹出 Google 登录并只持有短期、绑定受众的令牌。我们**不在本期**做它，但本期的表结构已为它留了接口（第 3.6 节末尾），它是**下一个任务 `accounts-oauth`**，并且会**有意**改掉 `/.well-known/*` 必须 404 的约定。请确认：本期先走 PAT，OAuth 2.1 作为下一期。
2. **「任何 Gmail 用户都能注册」可能做不到，取决于 Google 的发布规则。** 测试（Testing）状态下只有你手工列出的测试用户（约 100 个上限）能登录；转为正式发布可能要求你拥有的域名（主页与隐私政策），而 `vercel.app` 是公共后缀，**未必被接受**（**UNVERIFIED**）。因此第 8.3 节有一个**决策点**：要么注册一个自有域名（之后更新 `GEMARC_ACCOUNTS_BASE_URL` 与重定向 URI），要么接受 Testing 状态加 `GEMARC_ACCOUNTS_ALLOWED_EMAILS`——此时「注册」实质上是**邀请名单**，不是开放注册。请在投入 Google 控制台配置之前先想好选哪条。

### 0.1 用户已定的决定

1. **登录方式只有 Google 登录**（OpenID Connect 授权码流程）。**系统任何地方都不存放密码**：没有密码列、没有密码接口、没有密码重置流程。
   「密码加密保存」这一要求，用两件事满足：
   - 所有**机密凭据**（会话 ID、个人访问令牌）只存**哈希**（SHA-256，见第 4.5 节；输入是 256 位随机值，不需要密钥也不需要慢哈希），库里没有任何可直接使用的凭据；
   - 所有**个人信息**（邮箱、Google `sub`）做**字段级 AES-256-GCM 加密**；显示名**不请求、不存**（第 1.3 节）。
2. **「注册」= 一个被允许的 Google 账号第一次成功登录。**默认允许：邮箱域为 `gmail.com` 且 `email_verified` 为真；可配置。**默认策略给的是问责（谁拿了令牌），不是访问控制**：任何 Gmail 持有者都能注册并拿到只读令牌（第 3.4 节）。
3. **数据库**是经 Vercel Marketplace 开通的 **Neon Postgres**；连接串以环境变量到达（池化，TLS 要求见第 3.9 节）。数据库与 Google OAuth 客户端由**用户本人创建**、密钥由用户本人设置；代码、迁移、测试与分步说明由我们写。
4. **本期范围**：账号、**个人访问令牌（PAT）**（供 Claude Code / Codex / Hermes 以 `Authorization: Bearer` 调 `/mcp`）、审计日志、账号删除与数据导出。**不建**按用户的远程工程存储表。
5. **登录 = PAT 路径是一项决定，不是既成事实**（见 0.0 第 1 条，决定 D102/D103）。
6. **认证不等于授权**：能登录、能拿令牌，不等于能写。`write` 作用域不是自助项，只能由运营者 CLI 授予（第 3.4 节，D89）。

## 1. 数据清单与分级

### 1.1 分级

| 级别 | 含义 | 保护 |
|---|---|---|
| **C3** | 个人信息（邮箱、Google `sub`） | 字段级 AES-256-GCM 加密；盲索引仅用于查找 |
| **C2** | 凭据与伪匿名标识（会话/令牌哈希、IP 哈希、盲索引） | 带密钥的哈希，库中没有可直接使用的值 |
| **C1** | 运营元数据（时间戳、状态、作用域、事件类型） | 访问控制；不含 PII |
| **C0** | 公开信息（令牌的 8 位公开 ID） | 无 |

### 1.2 存什么、为什么存、存多久

| 表.字段 | 内容 | 为什么需要 | 级别 | 保留 |
|---|---|---|---|---|
| `users.id` | 随机 128 位（uuid4 的 32 位十六进制） | 内部主键；也是 AES-GCM 的 AAD 成分 | C1 | 到账号删除 |
| `users.sub_bidx` | `HMAC(blind_key, "sub\0"+sub)`，**UNIQUE** | 登录时按 Google `sub`（**唯一不变的账号键**）找到用户；并发双击登录由它的唯一约束裁决 | C2 | 到账号删除 |
| `users.sub_enc` | `sub` 的密文 | **只**用于更换密钥时重算 `sub_bidx` | C3 | 到账号删除 |
| `users.email_enc` | 邮箱（小写）的密文 | 账号页展示；运营者按邮箱处理数据主体请求；更换密钥时重算盲索引 | C3 | 到账号删除 |
| `users.email_bidx` | `HMAC(blind_key, "email\0"+email)`，**非唯一**索引 | 邮箱名单的策略复核；按邮箱查找而不存明文。**不再有 UNIQUE**：认证只认 `sub`，邮箱唯一性并不保护任何东西，反而在更新路径与并发注册上制造 500（评审修订） | C2 | 到账号删除 |
| `users.domain_bidx` | `HMAC(blind_key, "domain\0"+邮箱域)` | 域名单的**事后复核**（第 3.4 节）：窄化策略后不解密就能判断现有用户是否仍被允许；`rekey` 解密 `email_enc` 后重算 | C2 | 到账号删除 |
| `users.has_hd` | 0/1：ID 令牌是否带 `hd`（Workspace 账号） | 与 `domain_bidx` 一起复核域名单（`gmail.com` 条目要求 0，Workspace 条目要求 1 且域名相等）。**只存这一位**，不存 `hd` 原值 | C1 | 到账号删除 |
| `users.can_write` | 0/1，默认 0 | 运营者授予的写权限（第 3.4 节）；用户无法自助修改 | C1 | 到账号删除 |
| `users.bidx_kid` | 盲索引所用密钥版本 | 轮换期间知道用哪把钥匙重算 | C1 | 同上 |
| `users.status` | `active` / `disabled` | 运营者封禁；**在登录、会话、PAT 三处都被强制** | C1 | 同上 |
| `users.created_at` `last_login_at` | 秒级 epoch | 账号页展示、清理僵尸账号 | C1 | 同上 |
| `sessions.id_hash` | `SHA-256("session\0"+sid)` 的 base64url | 登录态；**库里没有 sid 明文**（输入是 256 位随机，无需密钥，见第 4.5 节） | C2 | 过期 + 1 天 |
| `sessions.user_id` `created_at` `last_seen_at` `idle_expires_at` `expires_at` | 关联与过期 | 空闲/绝对超时由服务端强制；`created_at` 同时是「近期登录」判据 | C1 | 同上 |
| `api_tokens.id` | PAT 的 8 位公开 ID | 令牌前缀里的查找键，可显示、可入日志 | C0 | 撤销/过期后 30 天 |
| `api_tokens.secret_hash` | `SHA-256("pat\0"+secret)` 的 base64url | 校验令牌；**库里没有令牌明文**；**没有 `hash_kid`**（不依赖密钥环，轮换主密钥不会使令牌失效） | C2 | 同上 |
| `api_tokens.kind` | 固定 `pat`（默认值） | 给将来 OAuth 2.1 的令牌类型留的标记（第 3.6 节末尾），本期只有一种 | C1 | 同上 |
| `api_tokens.name` `scope` `created_at` `expires_at` `last_used_at` `revoked_at` | 用户给的标签（≤ 40 字符，页面提示「别写机密」）、`read`/`write`、时间 | 用户管理自己的令牌 | C1 | 同上 |
| `audit_log.*` | `id` `ts` `event` `user_id`（可空）`ip_hash`（可空）`ref`（可空）`code`（可空） | 事后追查与滥用检测 | C1/C2 | **最长 30 天**（可配 7–90；**前提是服务有流量或运营者跑 `gc`**，见第 5.6 节） |
| `rate_limits.*` | `key_hash` `window_start` `count` | 限流；`key_hash` 是 `HMAC(ratelimit 子密钥, 作用域+"\0"+主体)` | C2 | 约 2 天（同上前提）；账号删除时**按用户的键一并删除**（第 3.12 节） |
| `oauth_states.*` | `state_hash` `nonce_hash` `binding_hash` `created_at` `expires_at` | 登录 CSRF/重放防护；**不存 PKCE 验证器**（由 state 与浏览器 Cookie 值现算，第 3.3 节） | C2 | **10 分钟**，用后即删（同上前提） |
| `schema_migrations.*` | 版本、校验和 | 迁移记录 | C1 | 永久 |

### 1.3 **刻意不存**的东西（最小化）

| 不存 | 理由 |
|---|---|
| **密码 / 密码哈希** | 没有密码登录 |
| **显示名 `name`** | **不请求 `profile` 范围**（只请求 `openid email`）：显示名只为问候语，去掉一个 PII 字段，也去掉一个 XSS 反射点 |
| **头像 `picture` URL** | 展示不需要；链接到第三方可被用作追踪像素 |
| **Google 的 `access_token` / `refresh_token` / `id_token`** | 我们不调用任何 Google API；换完码、读完 `id_token` 即丢弃（只在内存里活几毫秒）。不请求 `access_type=offline`，所以根本不会得到刷新令牌 |
| **`hd` 原值 / 邮箱域明文** | 只存 `domain_bidx`（盲索引）与 `has_hd`（一位），用于策略复核；邮箱域不以明文落库 |
| **明文 IP** | 只存**按日加盐的带密钥哈希**（第 3.7 节），IPv6 先截到 /64 |
| **User-Agent、语言、地区** | 没有用途 |
| **邮箱的任何明文索引或日志** | 日志只写事件编号（I6） |
| **会话表里的 IP / UA** | 不提供「设备列表」功能，也就不需要 |
| **PKCE 验证器** | 不落库：`code_verifier` 由 state 与浏览器 Cookie 值现算（第 3.3 节），因此也不需要为它加密 |

### 1.4 保留与删除

- 账号存续期间：`users`、`sessions`、`api_tokens`。**账号删除是硬删除**（第 3.12 节）。
- 审计日志最长 30 天滚动删除；账号删除时其审计行**匿名化**（`user_id` 外键置空；`ip_hash` 与 `ref`（令牌公开 ID）置空），事件类型与精确时间戳保留至到期。**删除后仍残留的伪匿名数据**（不要写成「什么都不剩」）：这些审计行的事件类型与时间；按 IP 哈希计数的 `signup_ip`/`login_*` 限流行（不属于「按用户」的键，最多约 2 天，由保留清理删除）；Neon 备份。
- 过期的会话、`oauth_states`、`rate_limits`、已撤销/过期超过 30 天的令牌：由**有界的机会式清理**删除（第 5.6 节）。**诚实的保留表述**：上面各表的保留期是「**最长 N 天，前提是服务有流量**（清理在成功登录与令牌创建时顺带执行，每实例至多每 5 分钟一轮、每表每轮至多 200 行，见 `retention.py`）；没有流量时，要等下一次 `gc`」。要硬保证，运营者需要定期跑 CLI `gc`（第 5.6 节说明了为什么本任务不加 Vercel Cron）。
- **没有「不活跃自动清除」策略**（非目标，见第 10 节），建议以后补：24 个月未登录的账号删除。
- **备份**：Neon 的备份与时间点恢复会在其保留窗口内保留已删除的行（**调研**；窗口长度取决于 Neon 套餐）。**这个数字在你写隐私说明或删除承诺之前必须知道**：第 8.2 节要求你读取该套餐的历史保留窗口并设为最小值，隐私文本必须写明「已删除的数据可能在备份中保留至多这么久」。字段加密**不是密码学擦除**（第 4.1 节）。
- **合规**：用户在日本，邮箱属于个人信息（APPI 要求公示利用目的）。本设计提供：未登录的 `/account` 页在 Google 登录链接**之前**显示一段中文告知（存什么、为什么、保留多久、如何导出与删除），并可链接运营者自己的隐私声明（`GEMARC_ACCOUNTS_PRIVACY_URL`，可选，必须是 https）；另提供导出与删除。**隐私声明的正文由运营者撰写**，不在本设计范围，也不是法律意见。

## 3. 架构

### 3.0 开关解析与「登录意图」（单一纯函数）

**设计决定（评审后新增，D86/D87）**：所有安全意图类环境变量都按**三态**解析，解析与「登录意图」的判定只写在 `src/gemarc_mcp/accounts/flags.py`（仅标准库，无任何第三方导入；`accounts/__init__.py` 为空）。`api/index.py` 的禁用分支与 `config.py` **共用同一个函数**，源码扫描测试断言 `api/index.py` 里不再出现对 `GEMARC_REQUIRE_LOGIN` / `GEMARC_MCP_AUTH` / `GEMARC_ACCOUNTS` 的直接 `os.environ` 读取。

**布尔类变量**（`GEMARC_ACCOUNTS`、`GEMARC_REQUIRE_LOGIN`，以及仅在账号启用后才校验的 `GEMARC_ACCOUNTS_ALLOW_SQLITE`、`_AUTO_MIGRATE`、`_DB_TLS_RELAXED`、`_DB_ROLE_RELAXED`、`_ACK_SHARED_WORKSPACE`、`_VERIFY_SIG`、`_MCP_HOST_ONLY`）：先 `strip()`（含 `\n`、空格、制表符），然后

| 值（strip 之后） | 结果 |
|---|---|
| 未设、空串 | off |
| `0` | off（明确的安全关闭字面量） |
| 恰好 `1` | on |
| 其它任何值（`true`、`yes`、`on`、`TRUE`、`01`、`2`、`enabled`……） | **bad（配置错误）** |

**这张表的可见后果（acct-fix 说明）**：`GEMARC_ACCOUNTS=true`、`yes`、`TRUE` 等任何非 `0`、非 `1` 的值**不是「关」而是配置错误**：账号被视为「存在但不可用」，于是 `/healthz` 多一个 `accounts:"misconfigured"` 键，`/account`、`/auth/google/start` 答 503（带安全响应头，不是 404），`/mcp` 不受影响（有登录意图时才 503）。这是有意的失败关闭（D86），不是安全问题，只是与「完全不设」不逐字节相同。带前后空格的 ` 1` 在 `strip()` 之后算 `1`（开）。

**`GEMARC_MCP_AUTH`**：先 `strip()`；空/未设 = unset；否则**大小写敏感**地匹配 `none` / `env-token` / `pat` / `pat-or-env`，其它（`PAT`、`Pat`、`token`、`pat,env`……）= **bad**。

**测试矩阵（实现任务直接照抄）**：对 `GEMARC_ACCOUNTS` 与 `GEMARC_REQUIRE_LOGIN` 各取 `未设`、`""`、`" "`、`"0"`、`"1"`、`"1 "`、`" 1"`、`"1\n"`、`"true"`、`"yes"`、`"TRUE"`、`"on"`、`"01"`、`"2"`；对 `GEMARC_MCP_AUTH` 各取 `未设`、`""`、`"none"`、`"env-token"`、`"pat"`、`"pat "`、`"pat-or-env"`、`"PAT"`、`"Pat"`、`"token"`、`"pat,env"`。期望：前一类中 `未设/""/" "/"0"` → off，`"1"/"1 "/" 1"/"1\n"` → on，其余全部 → bad；后一类中前五项合法值（含 `"pat "` 去空白后即 `pat`）按取值映射，`PAT`/`Pat`/`token`/`pat,env` → bad。对每个 bad 值再断言**最终行为**（下表），**绝不能出现 `/mcp` 开放**。

**有效 `/mcp` 模式的求值**（在 flags 里一并算出，`GEMARC_MCP_TOKEN` 的取值规则不变：非空 = 有环境令牌）：

| 输入 | 有效模式 |
|---|---|
| `REQUIRE_LOGIN` off，`MCP_AUTH` unset | 沿用今天：有环境令牌 → `env-token`，否则 `none` |
| `REQUIRE_LOGIN` on，`MCP_AUTH` unset | 有环境令牌 → `pat-or-env`，否则 `pat` |
| `MCP_AUTH=pat` / `pat-or-env`（`REQUIRE_LOGIN` off 或 on） | 如其所设 |
| `MCP_AUTH=none` 且 `GEMARC_MCP_TOKEN` 非空 | **冲突**（既说开放又设了令牌） |
| `MCP_AUTH=env-token` 且没有 `GEMARC_MCP_TOKEN` | **冲突**（没有可比对的令牌，退化为开放） |
| `REQUIRE_LOGIN` on 且 `MCP_AUTH` 为 `none`/`env-token` | **冲突**（自相矛盾） |
| `MCP_AUTH=none`（无令牌）/ `env-token`（有令牌），`REQUIRE_LOGIN` off | 如其所设 |
| 任何 bad | **bad** |

**登录意图（login intent）** = `REQUIRE_LOGIN` 不是 off（含 bad），**或** 有效模式含 `pat`（`pat`/`pat-or-env`），**或** `MCP_AUTH` 是 bad，**或**出现上表的任何「冲突」。

- 意图为真且（账号不是 on，**或**配置不完整，**或**出现 bad/冲突）→ `/mcp` 对**每个**请求答 **503 `GEMARC_ACCT_001`**，不看环境令牌，**绝不退回开放**。
- **有意不算意图**：单独设置 `GEMARC_ACCOUNTS=1`（或 bad），或预先设置 `GEMARC_ACCOUNTS_BASE_URL` / `_KEYS` / `GOOGLE_*` 等 `GEMARC_ACCOUNTS_*` 变量。理由：账号功能本身**不改变 `/mcp` 的认证**；运营手册第 8.5 节**要求**先设这些变量、最后才设 `GEMARC_ACCOUNTS`，而第 8.9 节第 1 步要求此时部署后行为**与今天完全一致**，所以把它们算作意图会让暂存部署 503，且并不会挡住任何旁路（没有任何登录要求在起作用）。`GEMARC_ACCOUNTS` 本身为 on/bad 时的行为见第 3.6 节表格（账号路由 503，`/mcp` 仍沿用今天的规则）。**这是对评审意见的一处有意缩小**（第 12 节）。

- 「列出令牌」既在 `/account` 页上，也可 `GET /account/tokens` 单独渲染（HTML），没有 JSON API（本期不做给脚本用的账号 API，少一个攻击面）。
- 工具集没有写工具时，页面**不显示作用域选择**（只能是 `read`）。
- 所有 POST：`Content-Type` 必须是 `application/x-www-form-urlencoded`，正文 ≤ 8 KiB，用标准库 `urllib.parse.parse_qs` 解析。
- **每一个**账号响应（200/3xx/4xx/5xx，包括 421、429、503 与所有重定向）都**必须**经 `pages.py` 里**同一个**响应头函数，头集合为：`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: no-referrer`、`Cross-Origin-Opener-Policy: same-origin`、`Cross-Origin-Resource-Policy: same-origin`、`Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`、`Strict-Transport-Security: max-age=31536000`（仅 https 基址时）以及 CSP：

  ```
  default-src 'none'; style-src 'nonce-<每次响应随机>'; form-action 'self'; frame-ancestors 'none'; base-uri 'none'
  ```

  样式**只**用一个 `<style nonce="…">` 块；**不得**出现 `style=` 属性或内联事件处理器，**更不得**为图省事加 `'unsafe-inline'`。测试对「路由 × 状态码」整个矩阵断言头完整，并对渲染出的 HTML 扫描 `style=`/`on…=`。
- **`Host` 检查**：账号路由的请求 `Host` 必须等于配置基址的主机，否则答 421 `GEMARC_ACCT_001`（目的：避免在每个部署的独立 URL 上签发 Cookie；**这不是安全控制**，因为 Host 可伪造，安全控制是 I7）。`/mcp` 默认不做 Host 检查；`GEMARC_ACCOUNTS_MCP_HOST_ONLY=1` 时对**PAT 校验**做同样的检查（同样只是削减面）。
- 用户界面文字为中文，错误页带编号（见第 3.13 节）。

### 3.3 Google 登录流程

授权请求（**设计决定**）：

| 参数 | 值 | 说明 |
|---|---|---|
| `response_type` | `code` | 服务端授权码流程 |
| `client_id` | `GEMARC_GOOGLE_CLIENT_ID` | |
| `redirect_uri` | `GEMARC_ACCOUNTS_BASE_URL + /auth/google/callback` | 精确匹配；Google 不允许通配（**调研**） |
| `scope` | `openid email` | **不请求 `profile`**（数据最小化，D117） |
| `state` | 256 位随机 | 只存 `SHA-256("state\0"+state)` |
| `nonce` | 256 位随机 | 只存 `SHA-256("nonce\0"+nonce)` |
| `code_challenge` / `_method` | `S256`；`code_verifier = base64url(SHA-256("pkce\0"+state+"\0"+Cookie 值))`（43 字符），挑战 = `base64url(SHA-256(code_verifier))` | 验证器**不落库**，由回调时的 `state` 与浏览器 Cookie 值**现算**；它与浏览器 Cookie 绑定，所以没有 Cookie 就换不到令牌 |
| `prompt` | `select_account` | 让用户选账号（**不是**强重认证，第 3.5 节） |
| 不用 | `access_type`、`include_granted_scopes`、`login_hint`、`hd`、`response_mode` | `hd` 只是界面提示，不是访问控制 |

**为什么 `binding_hash` 与验证器用无密钥的 SHA-256**：Cookie 值本身是 256 位随机的机密值；无密钥哈希在 10 分钟的登录窗口内**不受密钥环轮换影响**（中途轮换不会让这次登录失败），也不需要「对密钥环里每把钥匙各算一遍」。

**发起**（`/auth/google/start`）：先过进程内限流（不碰库）→ 头检查（`Sec-Fetch-Mode`、`Sec-Fetch-Dest` 存在时必须分别是 `navigate`、`document`，否则 403 `GEMARC_ACCT_021`）→ **取浏览器绑定 Cookie**：若请求带有格式合法（43 个 base64url 字符）的 `__Host-gemarc_oauth` 就**复用**其值，否则生成新的 256 位随机值（因此第二个标签页开始的登录**不会**覆盖第一个标签页的绑定，每个 `state` 各有各的 `binding_hash`）→ 生成 `state`、`nonce` → 写 `oauth_states`（`state_hash`、`nonce_hash`、`binding_hash = SHA-256("bind\0"+state+"\0"+Cookie 值)`）→ 设 Cookie（https 基址：`__Host-gemarc_oauth`，`Max-Age=600`，`HttpOnly; Secure; SameSite=Lax; Path=/`；http 回环基址（仅开发与测试）：`gemarc_oauth`，无前缀、无 `Secure`，其余相同，与第 3.5 节会话 Cookie 同一规则）→ 302。

**回调**（`/auth/google/callback`）按此顺序。「拿到身份之前」的失败使用 010/011/012，「拿到身份之后」的**所有**拒绝对外只用 `GEMARC_ACCT_013`；审计里记录具体原因码：

1. 方法、限流、`Host`。
2. 有 `error` 参数 → 审计 `login_denied`（`idp_error`），错误页（012）；**前置 Cookie 不清除**（理由见第 11 步）。
3. `code`（≤ 512 字节）与 `state`（恰好 43 个 base64url 字符）必须存在；前置 Cookie 必须存在且格式合法（否则 011）。
4. **原子消费**：`DELETE FROM oauth_states WHERE state_hash=? RETURNING …`。不存在或已过期 → 010。重算 `binding_hash` 并常量时间比较；**不匹配也已消费**（攻击者不能重试）→ 011。
5. 回调带 `iss` 参数时必须等于 `https://accounts.google.com`。
6. 用 `code` + 现算的 `code_verifier` + `client_secret` POST 到 `https://oauth2.googleapis.com/token`（5 秒总期限、不跟随重定向、响应 ≤ 64 KiB、必须是 `application/json`、`token_type` 必须是 `Bearer`）。只取 `id_token`，其余字段丢弃。失败 → 012。
7. 校验 ID 令牌（下面的清单；`GEMARC_ACCOUNTS_VERIFY_SIG=1` 时先验签）。失败 → 013。
8. 域策略与邮箱名单（第 3.4 节）。不通过 → 013（审计 `domain`/`email_list`）。
9. 单个事务内（**换码在事务之外已完成**）：
   1. 按 `sub_bidx`（密钥环里每把钥匙各算一次，`IN (…)`）查用户。
   2. **已有**：`status != 'active'` → **013**，审计 `login_denied`（`disabled`），**不建会话、不更新 `last_login_at`**；否则若邮箱/`domain_bidx`/`has_hd` 变化则重加密并更新，写 `last_login_at`（并写 `email_changed`）。
   3. **没有**：检查按 IP 注册限流、再检查全局注册限流（**先 IP 后全局**，只有通过 IP 检查才消耗全局额度；任一不满足 → 013，审计 `closed`），然后在事务内检查总用户数上限（Postgres 上先取 `pg_advisory_xact_lock`，使上限检查与插入串行；**该路径未对真实 Postgres 验证**）；**邮箱复用**：若存在 `email_bidx` 相同、`sub_bidx` 不同且 `status='active'` 的旧行 → 停用它、删其会话、吊销其令牌，审计 `email_recycled`（第 3.4 节）；然后 `INSERT … ON CONFLICT (sub_bidx) DO NOTHING`，**再重查**：若是并发的同 `sub` 双击，则结果等同于「已有」分支，不会产生唯一约束异常。
10. 作废请求里带来的旧会话（若有），建新会话；超出每用户 5 个会话时删最旧的。
11. 写审计（`login_ok`，新用户另写 `user_created`）；设会话 Cookie；303 到 `/account`。**前置 Cookie 不清除，保留到它自己的 10 分钟到期**：它是每个浏览器一个、可复用的机密（D22），第二个标签页开始的登录还要靠它；它只有配合一次性、10 分钟的 `state` 才有用，保留它不扩大攻击面。

**ID 令牌校验清单**（**设计决定**；声明都取自 base64url 解码后的 JSON 载荷，用标准库解码，不依赖传递进来的 `pyjwt`）：

| 声明 | 规则 |
|---|---|
| 结构 | 恰好三段、载荷是 JSON 对象（解析时**拒绝重复键**）；`VERIFY_SIG` 关闭时头部与签名段**不解析、不信任** |
| `iss` | 恰好是 `https://accounts.google.com` 或 `accounts.google.com` |
| `aud` | 字符串且等于 `GEMARC_GOOGLE_CLIENT_ID`；若是数组，则必须含它，且 `azp` 必须等于它 |
| `azp` | 若存在，必须等于 `GEMARC_GOOGLE_CLIENT_ID` |
| `exp` | 必须是数值且 `exp > now − 60 秒`（时钟偏差容忍） |
| `iat` | 必须是数值且 `iat ≤ now + 60 秒`，并且 `now − iat ≤ 600 秒`（令牌刚从令牌端点拿到，应当很新） |
| `nonce` | 必须存在，`SHA-256("nonce\0"+nonce)` 与存放的 `nonce_hash` 常量时间相等 |
| `sub` | 必须是非空 ASCII 字符串，≤ 255 字符；**这是账号键** |
| `email` | 必须存在，且**恰有一个 `@`**；规范化为 `strip().lower()`；用于策略与展示，**不是**账号键 |
| `email_verified` | 必须是布尔 `true`；缺失、`false`、字符串 `"true"` 一律拒绝 |
| `hd` | 仅用于域策略与 `has_hd` 一位，**原值不入库** |

**为什么默认可以不验签（OIDC Core 3.1.3.7，并说明局限）**：令牌由本进程**直接从 Google 令牌端点经 TLS 取得**，并且用 `client_secret` 认证了我们自己，OIDC Core §3.1.3.7 允许此时用 TLS 服务器验证代替签名验证；Google 文档同样说明这一点（**调研**）。局限与对策（评审后修订，D24/D107）：

- 它**只**在「令牌直接来自令牌端点」时成立；将来若从浏览器、前端、别的服务接收 ID 令牌（如 One Tap、`id_token` 直传），**必须**验签。
- 安全性完全依赖 TLS 链：CA 存储、主机名校验、无企业代理拦截。所以 HTTP 客户端的下列性质**写成测试**：显式 `ssl.create_default_context()` 并断言 `verify_mode == CERT_REQUIRED` 与 `check_hostname`；自定义 `HTTPRedirectHandler` 遇到任何重定向直接抛错；只接受 https 且地址是模块常量；`token_type == "Bearer"`；`Content-Type` 为 JSON；不接受自定义 CA 环境变量。
- 它不防 Google 自身出错（T9）。
- **RS256 验签作为开关一并交付（不再是「本期不做」）**：`GEMARC_ACCOUNTS_VERIFY_SIG=1` 时，头部必须是 `alg=RS256` 与已知 `kid`，用 `cryptography` 验签；JWKS 取自常量地址 `https://www.googleapis.com/oauth2/v3/certs`（同一个加固过的 opener），缓存至多 1 小时，`kid` 未命中时最多每分钟重取一次；取不到或验不过 → 013（**关闭失败**）。**默认值本期为关**，因为 JWKS 抓取在 Vercel 上的耗时与 CA 行为尚未实测（**UNVERIFIED**）；第 8.11 节要求上线后测一遍再把它设为 `1`，使「CA 存储有问题」不会悄悄移动信任根。假 IdP 因此要提供 JWKS 与签名（第 7.1 节）。

### 3.4 注册、域策略与授权

**设计决定**：

- `GEMARC_ACCOUNTS_ALLOWED_DOMAINS`（逗号分隔，默认 `gmail.com`）。邮箱必须恰有一个 `@`，域 = `email.rpartition('@')[2]`，与条目做**精确相等**比较（不用 `endswith`，避免 `evilgmail.com`/`x@gmail.com.evil` 类缺陷）。对每个条目：
  - `gmail.com`（及运营者加入的 `googlemail.com`）：邮箱域等于条目，**且 ID 令牌里没有 `hd`**（消费者账号）。
  - 其它域（Workspace）：**`hd` 声明必须等于条目**，且邮箱域也等于它。
- `GEMARC_ACCOUNTS_ALLOWED_EMAILS`（可选，逗号分隔）：设置后，邮箱还必须**逐字符等于**名单里的某项（均规范化为 `strip().lower()`）。**不做** Gmail 点号/加号折叠（账号键是 `sub`，折叠只会制造冲突），所以 `john.doe@gmail.com` 与 `johndoe@gmail.com` 是**不同**条目：运营者必须写成 Google 实际返回的地址。被拒绝时，拒绝页会**显示登录者自己的邮箱**，以便他复制给你写进名单（审计里没有邮箱）。
- **默认策略的真实含义（务必知道）**：默认 `gmail.com` + 空名单 = **任何 Gmail 持有者都能注册并拿到只读令牌**。这是**问责**（谁拿了令牌、何时用），**不是访问控制**。如果希望 `/mcp` 只对指定的人开放，**必须**设 `GEMARC_ACCOUNTS_ALLOWED_EMAILS`（或 Workspace 域名单）。
- `GEMARC_ACCOUNTS_MAX_USERS`（默认 1000，`0` = 不限）：达到上限后**新注册**被拒（对外 013，审计 `closed`），已有用户仍可登录。它是**成本控制，不是滥用防御**。
- 注册限流：全局 60 个新用户/小时；**按 IP 哈希 3 个新用户/小时**；全局限额饱和时写一条 `signup_saturated` 审计（每小时至多一条）。**检查顺序是先按 IP、后全局**，只有通过 IP 检查的尝试才消耗全局额度；被 IP 限额拒绝的重试不会影响其他人的注册。
- **邮箱只属于一个活动行**：一个活动行持有的邮箱，如果被另一个 `sub` 首次注册带来，或被同一 `sub` 改成它，旧行都会被停用（会话删除、令牌吊销，审计 `email_recycled`）；两条路径共用同一个函数，行从不合并。
- 没有「邀请」与「审批」流程（非目标）；内测名单即 `ALLOWED_EMAILS`。运营者可用 CLI `disable-user` 封禁。

**停用用户（D88）**：`status != 'active'` 的用户——回调拒绝（审计 `disabled`，无会话、不更新 `last_login_at`）；会话查找 `JOIN users` 且要求 `status='active'`；PAT 校验要求 `status='active'`；已停用的用户创建 PAT 被拒。`disable-user` 在**同一个事务**里删光该用户的会话、把其 PAT 置 `revoked_at`。`enable-user` 仅恢复登录能力，**不**恢复已吊销的令牌。

**写权限不是自助项（D89）**：`users.can_write`（默认 0）只能由运营者 CLI `grant-write` / `revoke-write` 修改。`write` 作用域令牌只在**同时**满足下面三条时才能创建：`GEMARC_ALLOW_WRITE=1`、工具集含写工具、创建者 `can_write=1`；否则页面不提供、服务端拒绝（`GEMARC_ACCT_035`）。令牌的**有效作用域** = `min(令牌作用域, 用户当前 can_write)`。

**共享工作区规则（D90，配置完整性的一部分）**：工具集为 `full`（共享一个服务器工作区、无按用户隔离）+ 账号启用 + **开放注册**（`ALLOWED_EMAILS` 为空且 `ALLOWED_DOMAINS` 含 `gmail.com` 或 `googlemail.com`）→ **配置不完整**（503），除非运营者显式设 `GEMARC_ACCOUNTS_ACK_SHARED_WORKSPACE=1`。理由：否则每个注册的 Gmail 用户都能读那个共享工作区。

**策略的事后复核（D92）**：策略不只在登录时评估。启动时把当前策略算成**盲索引集合**（对密钥环里每个 kid 各一份）：邮箱名单 → `email_bidx` 集合；域名单 → `(domain_bidx, 需要的 has_hd)` 集合。**在会话查找时、以及 PAT 缓存未命中时**，用该用户已存的 `email_bidx` / `domain_bidx` / `has_hd` 对集合做成员判断（**不解密、不多一次查询**，因为这些列和用户行一起取回）。不在集合内 → 与停用同样处理。CLI `reconcile` 把不再合规的用户批量停用（同时删会话、吊销令牌）。**生效时间**：新部署用新环境，所以窄化策略后的下一次部署起，会话立即受影响，PAT 最迟在 `PAT_CACHE_SECONDS`（旧实例缓存）内受影响。

### 3.5 会话

| 项 | 值 |
|---|---|
| ID | 256 位随机（`secrets.token_bytes(32)` → base64url，43 字符），**只放 Cookie**，库里存 `SHA-256("session\0"+sid)` 的 base64url |
| Cookie 名 | https 基址：`__Host-gemarc_sid`（`Secure; HttpOnly; SameSite=Lax; Path=/`，**没有** `Domain`）；http 且主机是 `localhost`/`127.0.0.1`/`[::1]`（仅开发）：`gemarc_sid`，无 `Secure`，其余相同。基址是 http 且主机不是回环 → 配置不完整 |
| 是否持久 | 会话 Cookie（无 `Expires`/`Max-Age`）；真正的过期由服务端强制 |
| 先验格式后查库 | Cookie 值必须是 43 个 base64url 字符，**否则当作未登录且不碰数据库**；**没有 Cookie 的 `/account` 请求根本不碰数据库** |
| 查找 | `sessions JOIN users`，要求未过期、`users.status='active'`、且用户通过**当前策略复核**（第 3.4 节） |
| 空闲超时 | 默认 30 分钟（`GEMARC_ACCOUNTS_SESSION_IDLE_MIN`，5–240） |
| 绝对超时 | 默认 8 小时（`GEMARC_ACCOUNTS_SESSION_MAX_HOURS`，1–72） |
| `last_seen_at` 更新 | 距上次写入超过 5 分钟才写，避免每个 GET 都写库 |
| 轮换 | 登录成功时必换；账号状态变化（禁用、删除）时作废全部会话 |
| 并发上限 | 每用户 5 个，超出删最旧 |
| 撤销 | 登出删本行；`logout-all` 删该用户全部；账号删除级联删除；运营者禁用用户 → 全部作废（同事务） |
| 未知/过期的 ID | 视为未登录，**不**为它签发新 ID，清掉该 Cookie |
| 重复的同名 Cookie | 拒绝（视为未登录） |

OWASP 对低风险应用建议空闲 15–30 分钟、绝对 4–8 小时（**调研**）；会话只用于管理令牌的页面，MCP 调用走 PAT，所以取这个偏短的值。

**CSRF 令牌**：`HMAC(csrf 子密钥, sid)` 的 base64url，不入库，随表单隐藏域下发，常量时间比较。**校验时对密钥环里的每把钥匙都试一次**，所以渲染与提交之间发生密钥更换**不会**让这次提交失败。

**近期登录（step-up，D93）**：会话的 `created_at` 距今 ≤ 15 分钟。**以下动作都要求**：创建 PAT、全部撤销 PAT、全部登出、导出、删除账号。不满足则页面提示「请重新登录以确认」并给 `/auth/google/start` 链接（登录会轮换会话，所以这就是重新认证）。**诚实的说明**：这只是一次 Google 选账号点击（`prompt=select_account` 并不强制重新认证），一个已劫持且 Google 会话仍在的浏览器可以静默通过，所以它**不是强重认证**，只是把「偷到 Cookie」与「立刻铸出长寿命凭据」之间多隔了一道，并与「默认 30 天」「全部撤销」「审计」叠加。删除还须输入确认词 `DELETE`，且确认表单**显示完整邮箱**。Google 是否遵守 `prompt=login` 与 `max_age`（并返回 `auth_time`）**UNVERIFIED**；上线后实测，确认有效才把它们用于 step-up 流程并校验 `auth_time`，在那之前不声称强重认证。

### 3.6 `/mcp` 如何认证

**模式**（有效模式的求值见第 3.0 节）：

| 模式 | 行为 | 碰数据库 |
|---|---|---|
| `none` | 开放（今天的 authless） | 否 |
| `env-token` | 只认 `GEMARC_MCP_TOKEN`（今天的行为） | 否 |

**默认不破坏**：`GEMARC_MCP_AUTH` 与 `GEMARC_REQUIRE_LOGIN` 都未设 → 完全沿用今天的规则（`GEMARC_MCP_TOKEN` 非空 = `env-token`，否则 `none`）。账号功能本身**不会**改变 `/mcp` 的认证，必须由运营者显式选 `pat` 或 `pat-or-env`，或设 `GEMARC_REQUIRE_LOGIN=1`。

**`GEMARC_REQUIRE_LOGIN=1`**：运营者声明「`/mcp` 必须要求账号凭据」。有效模式 = `pat-or-env`（设了 `GEMARC_MCP_TOKEN`）或 `pat`（没设）。与显式的 `GEMARC_MCP_AUTH=none|env-token` 同时出现，视为**自相矛盾的配置**（第 3.0 节）。

**关闭失败矩阵**（`flags` 与 `config` 求值之后；「意图」的定义见第 3.0 节）：

**`/healthz` 公开面（D5/D119，评审后收窄）**：只有 `accounts`（`ok` / `misconfigured` / `db-unreachable`）与 `authRequired`（含义不变：存在任何形式的强制认证，**或**登录意图为真，即为 `true`）。**不**公开 `accountsMissing`（缺失的变量名）、`mcpAuth`（有效模式）、数据库角色、TLS 警告：它们等于免费侦察。这些只在运营者 CLI `status` 里给出，以及日志里一条只带**事件编号**的记录。

**PAT 格式**：`gat_<8 位公开 ID>_<43 位密钥><6 位校验和>`，总长 **62**，**按固定位置解析**（因为 base64url 的密钥里可能含 `_`，不能按 `_` 切分）：

```
gat_ k3x7q2mn _ <43 chars base64url of 32 random bytes> <6 chars checksum>
0..3 4..11     12  13..55                                56..61
```

- 公开 ID：5 个随机字节的小写 base32（字母表 `a-z2-7`，8 字符），`api_tokens.id`，冲突则重抽（最多 3 次）。
- 密钥：`secrets.token_bytes(32)`。
- **校验和**：`base64url(CRC32(前 56 个 ASCII 字符的字节)，4 字节大端)`，6 个字符。作用是**挡手误**（先于任何缓存与数据库访问就拒绝），**不是安全控制**，不防伪造。
- 库存 `SHA-256("pat\0"+secret)` 的 base64url。**从不存密钥**；明文只在创建那次响应里出现，页面带 `no-store`。
- **密钥扫描器**：不声称「`gat_` 前缀会被扫描器自动识别」（那需要向各平台注册）。我们发布一条固定正则 `gat_[a-z2-7]{8}_[A-Za-z0-9_-]{49}`，供运营者加进自己的 gitleaks / trufflehog 规则；公开仓库场景可另行申请 GitHub secret scanning 合作伙伴注册。
- 创建参数：名称 ≤ 40 字符；作用域 `read`（默认）或 `write`（仅当第 3.4 节三个条件都满足；`write` 含 `read`）；有效期**默认 30 天、默认上限 90 天**（`GEMARC_ACCOUNTS_PAT_DEFAULT_DAYS`、`GEMARC_ACCOUNTS_PAT_MAX_DAYS`，运营者最多把上限调到 365）、**没有永不过期**；每用户最多 10 个有效令牌；创建限流 10 次/小时/用户；**创建要求近期登录**（第 3.5 节）。

**PAT 校验算法**（评审后重排；失败限流**放在缓存之后**）：

1. 取 `Authorization: Bearer <t>`（沿用现有 `_presented_token`，**只读头**）。`pat-or-env`：先与环境令牌常量时间比较，命中即过。
2. 格式 + 校验和检查：长度 62、前缀 `gat_`、位置 12 是 `_`、公开 ID 在 base32 字母表内、密钥在 base64url 字母表内、校验和相等。**失败直接 401，不查库、不查缓存**（内存里记一次失败）。
3. `digest = SHA-256("pat\0"+secret)`。**正缓存**（键 = 公开 ID + digest，**不存令牌本身**）命中且未过期 → 通过（缓存里同时带着有效作用域与用户 ID）。
4. **负缓存**（键 = 同上，默认 15 秒，`GEMARC_ACCOUNTS_PAT_NEGCACHE_SECONDS`，0–60，有界 LRU 1024）命中 → 401，**不查库**。
5. **失败限流只放慢、不判死刑**：该 IP 的内存失败计数超过阈值（30 次/5 分钟）时，未命中缓存的校验只能走一个**单槽「惩罚通道」**；槽被占用则 429 + `Retry-After`。**诚实的措辞**：已在正缓存里的有效令牌**永远不会**被限流挡住；缓存未命中的令牌在无法知道它是否有效之前必须走校验，所以在攻击者恰好占满同一 IP 的惩罚通道时它可能得到一次 429，重试即可。没有受信 IP 时不设 IP 限流（用每实例宽松桶）。
6. **单飞**：同一 `digest` 的并发未命中共享**一次**数据库查询（其余等待其结果）。
7. 在 **PAT 预留执行器**里开一个短事务：`SELECT … FROM api_tokens JOIN users WHERE api_tokens.id = ?`；用 `hmac.compare_digest` 比较存放的哈希与算出的 digest（行不存在则直接失败；**不做「虚拟 HMAC 拉平时间」**，因为公开 ID 本来就不是机密，那样做什么也保护不了）；检查 `revoked_at IS NULL`、`expires_at > now`、`users.status = 'active'`、用户通过**当前策略复核**（盲索引集合，第 3.4 节）。
8. 失败 → 401（响应体与今天完全一致，**不区分**无效/过期/已撤销/已停用/不在策略内，原因只进审计）、写负缓存、内存失败计数加一；**仅当计数越过阈值**才写 DB 计数与审计（`token_auth_failed`，按 IP 哈希 5 分钟去重）。
9. 成功 → 写正缓存（`min(TTL, 令牌剩余寿命)`），`last_used_at` **只在距上次超过 1 小时才写**（与校验同一事务）。

**撤销生效延迟（设计决定）**：进程内正缓存 TTL 默认 **30 秒**（`GEMARC_ACCOUNTS_PAT_CACHE_SECONDS`，范围 0–120，`0` = 不缓存）。因此**撤销、停用、写权限回收在每个函数实例上最迟 TTL 内生效**；处理撤销请求的那个实例立即驱逐。缓存有界（最多 512 项，LRU）。**Neon 与算力的取舍**：PAT 模式下每个缓存未命中都会唤醒 Neon（自动缩零的计算时间，免费档按小时计）；想少唤醒可以调大 TTL，代价是撤销更慢。**拒绝**「只读令牌用更长缓存」的建议：撤销延迟对只读令牌同样重要，且会让两类令牌行为不一（第 12 节）。

**作用域执行（允许名单，D46/D91）**：作用域只能**收窄**，`GEMARC_ALLOW_WRITE` 仍是总开关。

- **工具集没有写工具**（默认 `stateless`）：作用域**无意义**——**不缓冲、不解析请求体**，页面不显示作用域列，`write` 令牌不能创建。
- **工具集含写工具**（`full`）且**有效作用域**为 `read`：HTTP 层缓冲请求体（上限 `MAX_MODEL_BYTES` 加开销，沿用 `_drain` 的上限与超时思路），按**允许名单**判定，不是拒绝名单：
  - 只允许的方法：`initialize`、`ping`、`notifications/*`、`tools/list`、`resources/list`、`resources/templates/list`、`resources/read`、`prompts/list`、`prompts/get`，以及 `tools/call` 且工具名属于 **「构建时从注册表读出的已注册工具名（`REGISTERED_TOOLS`）减去 `WRITE_TOOLS`」**（不是手写清单）。**如实说明的残余依赖**：`WRITE_TOOLS` 来自 `server.py` 注册工具时的 `write=` 标志，一个忘了标 `write=True` 的新写工具会被当成只读；因此测试把「`full` 工具集里的只读工具集合」钉成一份**经评审的字面量清单**，并断言每个工具的 `readOnlyHint` 与 `WRITE_TOOLS` 一致——新增工具会让这个测试失败，迫使人工审阅其读/写性质。
  - 其它**任何**方法、未知工具名、缺失/非字符串的 `params.name` → 403 `{"error":"insufficient_scope","code":"GEMARC_ACCT_032"}` 与 `WWW-Authenticate: Bearer error="insufficient_scope"`，审计 `token_scope_denied`。
  - 解析规则（防解析器差异绕过）：请求体必须是合法 UTF-8 且**无 BOM**；JSON 解析使用 `object_pairs_hook`，**遇到重复键直接拒绝**；顶层必须是 JSON 对象，或**非空**的对象数组，批量里的**每个**成员都要过允许名单，出现非对象成员 → 拒绝。
  - **转发的是刚才被解析的那份原始字节**（用同一个缓冲区重放），**绝不重新序列化**。
- **本期不做**按用户隔离的工作区：`full` + 写仍不建议在公开部署启用（OPS-001 第 7 节），并受第 3.4 节「共享工作区规则」约束。

**claude.ai 自定义连接器与将来的 OAuth 2.1（D83/D102/D103，UNVERIFIED，调研）**：

- 连接器只支持 **OAuth** 或**无认证**；静态请求头只是部分组织可用的 beta。**PAT 是 `Authorization: Bearer` 头，所以 claude.ai 连接器用不了**；它们仍可用 authless（`GEMARC_MCP_AUTH=none`）。
- **PAT 是「没有 OAuth 的客户端」的通道**，不是长期的最终形态。支持 MCP 授权规范的客户端应当改走 OAuth 2.1，直接用 Google 登录并只持有短期、绑定受众的令牌。这是**下一个任务 `accounts-oauth`**：`/.well-known/oauth-protected-resource`（RFC 9728）并在 401 的 `WWW-Authenticate` 里带 `resource_metadata`、授权服务器元数据（RFC 8414，含 `code_challenge_methods_supported: ["S256"]`）、`authorize`/`token` 端点、动态客户端注册或客户端 ID 元数据文档、`resource` 参数（RFC 8707）、按受众绑定的短期令牌 + 轮换的刷新令牌（新迁移加 `oauth_clients`、`oauth_codes`、`oauth_refresh_tokens`）。
- **本期为它预留、使它不需要改本期表结构的接口**：`users` 与 `sessions` 原样复用（`/authorize` 内部的登录一步就是本期的 Google 登录 + 会话）；`api_tokens.kind` 已标为 `pat`，OAuth 令牌将落在自己的表里，校验分派按令牌形态/`kind` 进行；`pat` 的缩短寿命与近期登录要求保持不变。
- **这会有意打破** `test_oauth_discovery_probes_get_a_clean_404` 与「`/.well-known/*` 必须 404」的约定（I5），所以**不在本期**；到那时必须先改这些测试并同步 OPS-001 第 4 节。

### 3.7 限流、IP 处理与拒绝服务

**分层（D96）**：

0. **平台层**：在函数前面放 **Vercel Firewall** 的限速规则，覆盖 `/auth/*`、`/account*`、`/mcp`（套餐是否提供、额度多少 **UNVERIFIED**）；运营手册写明**Attack Challenge Mode** 作为紧急开关（第 8.11 节）。
1. **进程内每实例令牌桶**（不碰库）：**先**检查它；只有它放行，才去写库。
2. **库内固定窗口计数器**（跨实例）：`window_start = now − now % 窗口`；`INSERT … ON CONFLICT (key_hash, window_start) DO UPDATE SET count = count + 1 RETURNING count`；键是 `HMAC(ratelimit 子密钥, 作用域 + "\0" + 主体)`，所以表里没有明文 IP 或用户 ID。固定窗口在边界处可能放行 2 倍突发（已知取舍）。**例外**：`pat_auth_fail` 只在**内存**里累加，仅当越过阈值才写库（匿名洪水不应该变成数据库写）。

| 作用域 | 主体 | 上限 | 窗口 | 存放 |
|---|---|---|---|---|
| `login_start` | IP 哈希 | 20 | 10 分钟 | 先查内存、通过后再写 DB |
| `login_callback` | IP 哈希 | 30 | 10 分钟 | 同上 |
| `signup_global` | 全局 | 60 | 1 小时 | DB |
| `signup_ip` | IP 哈希 | 3 | 1 小时 | DB |
| `pat_create` | 用户 | 10 | 1 小时 | DB |
| `pat_auth_fail` | IP 哈希 | 30（只数失败） | 5 分钟 | **内存**，越阈值才写 DB |
| `account_post` | 用户 | 60 | 10 分钟 | DB |
| `export` | 用户 | 5 | 1 天 | DB |
| `delete_attempt` | 用户 | 5 | 1 天 | DB |
| 每实例预过滤（账号路由） | IP 哈希；无可信 IP 时用 `no-ip:` + 连接地址/UA/Accept 的短哈希 | 120（无可信 IP 的键 300） | 1 分钟 | 内存 |

超限 → 429 + `Retry-After`、`GEMARC_ACCT_022`。

**IP 来源与哈希（D99，评审后收紧）**：

- **只信 `x-vercel-forwarded-for`**，并且仅当环境变量 `VERCEL` 存在**且**该请求头存在。是否被 Vercel 覆盖客户端自带的值 **UNVERIFIED**：运营手册要求上线后用**伪造该头**的 `curl` 自查（第 8.11 节），测试里用假头验证取值逻辑。
- **永不读 `x-real-ip`**；`x-forwarded-for` 仅当运营者显式设置 `GEMARC_ACCOUNTS_TRUSTED_PROXY_HOPS=N`（1–5）时才读，取**从右数第 N 项**（不是第一项，第一项由客户端控制）。
- 没有可信 IP 时（不在 Vercel 上且没设 hop 数，或头缺失/非法），使用**每实例内存桶**，键是 `no-ip:` 加「连接地址 + `User-Agent` + `Accept`」的短哈希（不是全员共享的一个桶，所以一个吵闹的客户端锁不死别人；客户端改头就能换桶，所以这只是负载保护），**绝不**使用共享的 DB 桶。**代价**：此时按 IP 的 DB 限额（`login_start`、`login_callback`、`signup_ip`）整体不生效，配置检查给出 `no_trusted_client_ip` 警告。
- IPv4 取完整地址，IPv6 截到 /64。`ip_hash = HMAC(ip-hash 子密钥, 当天日期 + "\0" + IP)`，**按日更换盐**使得长期不能据此追踪同一来源；代价是审计里跨天不能关联同一 IP（有意）。

**数据库与执行器（D98）**：两个**独立**的有界线程池（`anyio` capacity limiter + 有界等待队列）：**PAT 校验执行器**（预留，如 6 个并发、队列 ≤ 24）与**匿名路由执行器**（小，如 3 个并发、队列 ≤ 6）。此外还有第三个很小的执行器专给**身份提供方的网络调用**（2 个并发、队列 ≤ 4），慢的上游因此饿不死数据库执行器。队列满 → 立即 **503 + `Retry-After` + `GEMARC_ACCT_023`**，**不排队堆积**，保证匿名洪水挤不掉 `/mcp` 的有效 PAT。

**其它省库手段**：会话 Cookie 先验格式再查库、无 Cookie 的 `/account` 不碰库（第 3.5 节）；PAT 的正/负缓存与单飞（第 3.6 节）。

**Neon 缩零与 PAT 模式的取舍（如实写出）**：`pat` / `pat-or-env` 模式意味着 `/mcp` 的缓存未命中会唤醒数据库；持续流量会让 Neon 计算常开、消耗免费档的算力小时；缩零后首个请求有冷启动延迟（R8）。

不记：邮箱、明文 IP、UA、令牌密钥、授权码。保留期与清理见第 1.4、5.6 节。

### 3.9 配置完整性判定

「完整」当且仅当下列**全部**成立（`config.py` 返回缺失/非法的变量名列表，不返回值）：

1. `GEMARC_ACCOUNTS` 解析为 on（第 3.0 节）；其余布尔类变量（`ALLOW_SQLITE`、`AUTO_MIGRATE`、`DB_TLS_RELAXED`、`DB_ROLE_RELAXED`、`ACK_SHARED_WORKSPACE`、`VERIFY_SIG`、`MCP_HOST_ONLY`）与 `GEMARC_REQUIRE_LOGIN`、`GEMARC_MCP_AUTH` 都**不是 bad**，且有效模式无冲突；
2. `GEMARC_ACCOUNTS_BASE_URL` 存在，是 `https://主机[:端口]`（无路径、无查询、无片段、无末尾 `/`）；仅当主机是 `localhost`/`127.0.0.1`/`[::1]` 时允许 `http://`；
3. `GEMARC_GOOGLE_CLIENT_ID`、`GEMARC_GOOGLE_CLIENT_SECRET` 非空（不是占位符）；
4. `GEMARC_ACCOUNTS_KEYS` 可解析：至少一项 `<kid>:<base64url 32 字节>`，kid 匹配 `[a-z0-9]{1,8}` 且互不相同，密钥解码后恰好 32 字节、不是全同字节；
5. 数据库地址存在且是 `postgres://`/`postgresql://`；**TLS（D101）**：主机**不是回环**时必须 `sslmode=verify-full` 并带 `sslrootcert`（`system` 或显式 CA 文件路径；配置检查不去验证文件或系统库是否存在）；**只有**明示 `GEMARC_ACCOUNTS_DB_TLS_RELAXED=1` 才接受 `sslmode=require`/`verify-ca`（二者只加密/只验链，不验主机名，主动中间人可冒充）；`disable`/`allow`/`prefer`/缺省**永远**不完整；主机是回环时不要求。`sqlite:///` 仅当 `GEMARC_ACCOUNTS_ALLOW_SQLITE=1`（开发与测试用；Vercel 上的 SQLite 文件在 `/tmp`，实例一换就没了，所以生产配置里不接受）；
6. 数值型变量都在其范围内；
7. **共享工作区规则**（第 3.4 节）：工具集为 `full` + 开放注册 → 必须 `ACK_SHARED_WORKSPACE=1`；
8. `GEMARC_ACCOUNTS_PRIVACY_URL` 若设置，必须是 https 地址；
9. **运行时角色**不是环境能判断的，所以**不属于**本清单，而是第一次用库时的运行时检测（第 3.10 节，`GEMARC_ACCT_004`）。

**警告**（不计不完整；只出现在 CLI `status` 与带事件编号的日志，不出现在公开的 `/healthz`）：数据库主机名不含 `-pooler`（Neon 的池化端点，**调研**）；`DB_TLS_RELAXED=1`；`DB_ROLE_RELAXED=1`；`VERIFY_SIG` 为 off；社区有报告说 Vercel 集成可能只注入直连地址（**调研**），此时请手动配置池化串。

### 3.10 数据库连接

- **每个工作单元一条短连接**，不做进程内连接池（函数实例短命，池化交给 Neon 的 PgBouncer）；阻塞的驱动调用放进第 3.7 节的两个有界执行器。
- **TLS**：Neon 页面给出的连接串带 `sslmode=require`；要满足第 3.9 节，运营者把它改成 `sslmode=verify-full&sslrootcert=system`（libpq ≥ 16 才支持 `system`；`psycopg[binary]` 3.2 自带的 libpq 版本与 Vercel 运行时的 CA 库是否支持 **UNVERIFIED**，上线核对清单第 8.11 节必须测它）。**退路**：不支持就设 `GEMARC_ACCOUNTS_DB_TLS_RELAXED=1` 并保留 `sslmode=require`（明示接受，残余风险见 R15）。配置测试断言上述每一种 `sslmode` 的判定。
- Neon 的池化端点是 PgBouncer **事务模式**（**调研**）：会话级 `SET` 不会保留，所以每个事务开头执行 **`SET LOCAL statement_timeout = '5s'`**（`SET LOCAL` 只在本事务内有效，事务模式下可用）。通过启动参数 `options=-c statement_timeout=…` 的做法经过 Neon 池化端点是否可用 **UNVERIFIED**，不采用。也可由运营者对应用角色执行 `ALTER ROLE gemarc_app SET statement_timeout = '5s'` 作为第二道保险。
- psycopg：`prepare_threshold=None`（关闭服务端预备语句；Neon 的 PgBouncer 支持协议级预备语句需要 ≥ 1.22，**调研**，关掉最稳）；`connect_timeout=5`；`autocommit=False`，一个 `with conn.transaction()` 一个工作单元。
- **运行时角色检测（D100）**：每个实例**第一次**用库时，在同一事务里多执行一条只读检查，结果在实例内缓存：当前用户**是 `users` 表的拥有者**、或对 `public` 模式有 `CREATE`、或对 `users` 有 `TRUNCATE` → 判为 `privileged`。`privileged` 且未设 `GEMARC_ACCOUNTS_DB_ROLE_RELAXED=1` → 拒绝后续库操作并回 `GEMARC_ACCT_004`。SQLite 后端视为 `app`。
- 不使用：会话级咨询锁、`LISTEN/NOTIFY`、临时表、`WITH HOLD` 游标、SQL 级 `PREPARE`（均不兼容事务池，**调研**）。迁移用 `pg_advisory_xact_lock`（事务级，可用）。
- 迁移必须用**直连**地址（`DATABASE_URL_UNPOOLED`，Neon 文档要求迁移走直连，**调研**）；**该地址是拥有者凭据，只应在你的机器上用，不应留在项目的 Production 环境里**（第 5.4、8.8 节）。
- 数据库地址的选取顺序：`GEMARC_ACCOUNTS_DATABASE_URL` → `DATABASE_URL` → `POSTGRES_URL`。Neon 页面列出的变量是 `DATABASE_URL`（池化）与 `DATABASE_URL_UNPOOLED`（直连），可选的 `PG*`；**没有**提到 `POSTGRES_URL`，把它当作旧版本集成的兜底（**UNVERIFIED**）。
- **错误处理（I6）**：每个账号路由与 PAT 校验器外面包**顶层兜底**，只记事件编号与异常**类名**，回通用 500/503；**不记录**异常文本（Postgres 的 `DETAIL` 可能带键值）；`gemarc_mcp.accounts` 内禁用 `log.exception` 与 `exc_info`。
- 在 Fluid 计算下实例可能被复用（**调研**），但设计**不依赖**复用。

### 3.11 响应、错误与页面

浏览器页面（`/account`、错误页）为服务端渲染的最小 HTML：中文文案、无 JS、`<style nonce>` 块（无 `style=` 属性）、所有动态值经 `html.escape`。头集合由第 3.2 节的唯一函数施加。未登录的 `/account` 在「使用 Google 登录」链接**之前**显示一段中文告知（存什么：邮箱，加密存放；为什么：识别你的账号、签发令牌；保留多久；如何导出与删除），并在设置了 `GEMARC_ACCOUNTS_PRIVACY_URL` 时链接运营者的隐私声明。`/mcp` 的错误保持 JSON。`/account/export` 是 `application/json` 附件（`Content-Disposition: attachment`，`no-store`）。

### 3.12 账号删除与数据导出

**导出**（`POST /account/export`，**要求近期登录**）：返回一个 JSON 文件，字段：`schema`（版本号）、`exportedAt`、`profile`（`email`，解密后的明文）、`createdAt`、`lastLoginAt`、`sessions`（`createdAt`、`lastSeenAt`、`expiresAt`，**不含哈希**）、`tokens`（`id`、`name`、`scope`、`createdAt`、`expiresAt`、`lastUsedAt`、`revokedAt`，**不含哈希**）、`audit`（`ts`、`event`、`code`、`ref`，**不含 IP 哈希**）。永远不含任何凭据。限流 5 次/天；写一条 `export` 审计。

**删除**（`POST /account/delete`）：要求会话是近 15 分钟内登录的、CSRF 通过、表单里输入确认词 `DELETE`（表单显示完整邮箱）。**硬删除**，一个事务内：

1. `UPDATE audit_log SET ip_hash = NULL, ref = NULL WHERE user_id = ?`（匿名化；`ref` 是令牌公开 ID，删除后不再保留）；
2. `DELETE FROM rate_limits WHERE key_hash IN (<该用户 ID 在每个「按用户」作用域下的键哈希>)`——键由 `user_id` 与固定的作用域列表**现算**，因此这些伪匿名行**不会**在删除后残留（D109）；
3. `DELETE FROM users WHERE id = ?`——`sessions`、`api_tokens` 经 `ON DELETE CASCADE` 一并删除，`audit_log.user_id` 经 `ON DELETE SET NULL` 置空；
4. 写一条**不带 `user_id`** 的 `account_deleted` 审计；
5. 清会话 Cookie，渲染「已删除」页。

**删除后仍残留的东西（如实列出，都是伪匿名的）**：这些审计行的事件类型与精确时间戳；按 IP 哈希计数的限流行（`signup_ip`、`login_*` 不在「按用户」的作用域里，最多约 2 天，由保留清理删除）；Neon 备份。

SQLite 默认不强制外键，适配器**必须**执行 `PRAGMA foreign_keys = ON`，并有测试覆盖级联。删除后同一个 Google 账号再次登录会创建**全新**账号（新 `id`）。我们不调用 Google 的撤销端点（我们没有它的令牌）；用户可在自己的 Google 账号设置里移除本应用授权。PAT 在删除事务提交时即失效，但各实例的缓存最多再活一个 TTL。**Neon 备份在其保留窗口内仍含旧行**（第 1.4、10 节）：隐私文本必须如实写出该窗口。

## 4. 密码学方案

### 4.1 Neon 已经做的与字段加密多做的

| | Neon 静态加密 | 字段级 AES-GCM（本设计） |
|---|---|---|
| 磁盘/快照被偷 | 防（**调研**，Neon 静态加密） | 防 |
| 备份、分支、导出文件落到别处 | 一般不防（备份由同一个平台持有） | **防**：没有密钥环读不出 PII |
| SQL 注入读表、只读角色被盗、`pg_dump` 被偷 | **不防**（对库来说是明文） | **防** |
| 预览分支/误开放的只读副本 | 不防 | 防 |
| 平台运营方的库侧访问 | 不防 | 防（但平台同时托管环境变量，见下） |
| 函数/环境变量被攻破（T6） | 不防 | **不防**（密钥就在那里） |
| 应用逻辑漏洞把 A 的数据返回给 B | 不防 | **不防** |
| 元数据（谁、何时、多频繁） | 不防 | 不防（时间、状态、条数是明文） |
| 删除后的备份残留 | 不防 | **不是密码学擦除**：同一密钥解得开所有旧备份 |

结论：字段加密把「**库泄露**」与「**环境泄露**」分成两个独立事件，攻击者要同时拿到两者才能读到 PII；它**不是**对抗应用被攻陷的手段。

### 4.2 决定：一个主密钥 + HKDF，而不是多个环境变量

**设计决定**：运营者只管理**一个密钥环变量** `GEMARC_ACCOUNTS_KEYS`，里面每项是一个版本化的 256 位主密钥；活动密钥（第一项）经 **HKDF-SHA256**（RFC 5869）派生出各用途的子密钥：

```
子密钥 = HKDF-SHA256(ikm = 主密钥, salt = b"gemarc-accounts-v1", info = b"gemarc/accounts/v1/<用途>", length = 32)
用途 ∈ { field-enc, blind-index, csrf, ip-hash, ratelimit }
```

（评审后：原先的 `token-pepper` 用途**取消**——会话与 PAT 改用无密钥的 SHA-256，见第 4.5 节。）

理由：

1. **轮换是一个动作**。多个独立密钥意味着多套轮换流程与多种出错方式；盲索引更换密钥要全表重算（需要解密每行），分开管理只会让运营者更容易漏掉一个。
2. **用途之间仍然独立**：HKDF 是单向的，泄露一个子密钥不暴露主密钥或其它子密钥；`info` 做域分离，同一把钥匙不会既加密又做 HMAC。
3. **安全边界相同**：多个环境变量与一个环境变量在同一个 Vercel 项目里，被读取的条件完全一样（T6）；分开存并不提高对环境泄露的抵抗。
4. **运营负担**：一个值要备份、一个值要设置，少一个遗漏点。
5. 代价：主密钥泄露 = 全部子密钥泄露。这与多变量方案在同一个项目里的实际风险一致，只有外部 KMS（Vercel 没有提供，**本期不做**）才能改善。
6. 密钥要求：恰好 32 随机字节；**拒绝**全同字节、过短、重复 kid；新增用途 = 新增 `info`，不动旧密钥。

### 4.3 字段加密（AES-256-GCM）

- 对象：**只有** `users.sub_enc`、`users.email_enc`（评审后：不再有 `name_enc` 与 `oauth_states.verifier_enc`）。
- **信封格式**（单个 TEXT 列）：`v1.<kid>.<base64url(nonce 12 字节)>.<base64url(密文‖16 字节标签)>`。
- **nonce**：每次加密 `os.urandom(12)`（96 位随机）。随机 nonce 的碰撞界限是同一密钥下约 2³² 次加密才到 2⁻³² 的碰撞概率。**策略**：同一把主密钥累计加密不超过 2²⁴ 次就轮换。**这条策略现在可以不靠计数器来保证**：加密只发生在**每用户**的少数几次（注册时 `sub_enc`+`email_enc`；邮箱变化时重加密 `email_enc`；`rekey` 时各一次），**匿名流量不再驱动任何加密**（PKCE 验证器已改为现算、不加密），所以累计次数有上界 `用户数 × (2 + 邮箱变更次数 + 2 × 轮换次数)`，在 `MAX_USERS`（默认 1000）下远低于 2²⁴。`status` 给出这个上界估计，不需要计数器。
- **AAD**：`b"gemarc-acct-v1|" + 表名 + b"|" + 列名 + b"|" + 行ID`。行 ID 在加密**之前**就生成好（`users.id`），所以插入时就能绑定。后果：把一行的密文搬到另一行或另一列，解密**必然失败**（有测试）。
- 解密：按信封里的 `kid` 在密钥环里找钥匙；找不到 → 明确的错误（`GEMARC_ACCT_002` 语义下的内部错误，不泄露 kid 之外的信息），**不是 500 也不是放行**。

### 4.4 盲索引（`sub_bidx`、`email_bidx`、`domain_bidx`）

- `HMAC-SHA256(blind-index 子密钥, 字段名 + "\0" + 规范化值)`，base64url。**`sub_bidx` 有 `UNIQUE` 约束；`email_bidx` 与 `domain_bidx` 是普通（非唯一）索引**（第 1.2 节）。
- 规范化：邮箱 `strip().lower()`；域 = 邮箱的 `rpartition('@')[2]`；`sub` 原样。
- **轮换**：盲索引密钥变了索引就变，**必须重算**，所以保存了 `sub_enc`、`email_enc` 供 `rekey` 解密后重算三个索引（`domain_bidx` 由解密出的邮箱重算；`has_hd` 是明文一位，不受影响）。轮换窗口内查找用 `IN (旧钥匙算的, 新钥匙算的)`，用户在 `rekey` 完成前也能登录；`users.bidx_kid` 记录当前索引由哪把钥匙生成；策略复核的集合按 kid 各备一份（第 3.4 节），所以复核在轮换期间也成立。
- 局限：邮箱空间可被字典枚举，若密钥环泄露，攻击者可对候选邮箱离线验证是否存在（A5）。盲索引**不**给出邮箱本身。

### 4.5 令牌与会话的哈希（评审后：无密钥）

- **会话**：`SHA-256("session\0"+sid)`；**PAT**：`SHA-256("pat\0"+secret)`；**state / nonce / 浏览器绑定 / PKCE**：`SHA-256("state\0"…)`、`"nonce\0"`、`"bind\0"`、`"pkce\0"` 各带固定的域分离前缀。输出一律 base64url。
- **为什么不用密钥（pepper）**：输入本身是 256 位随机，哈希泄露后既不能反推也不能穷举，密钥不增加任何安全性；它反而把令牌有效性**绑在会轮换的主密钥上**，使得「怀疑泄露而轮换」要么废掉全部 PAT，要么被迫把已泄露的密钥留在密钥环里。不需要慢哈希（bcrypt/Argon2）：它们为**低熵**口令设计，在这里只会拖慢每次 `/mcp` 调用。**不再有 `hash_kid`**，也就不存在「密钥环里找不到 `hash_kid`」这种状态。
- **仍然使用密钥的 HMAC**：盲索引（需要抗字典枚举）、CSRF 令牌、IP 哈希、限流键。CSRF 令牌**校验时对密钥环里每把钥匙都试一次**；其余三类在轮换时即时失效无副作用（盲索引靠 `rekey` 迁移；IP 哈希、限流键本来就是短期值）。
- **结论**：**主密钥更换从不使会话或 PAT 失效**，PAT 也不需要「`rekey` 迁移不了」的特殊处理（第 8.6 节随之简化）。

### 4.6 生成与保管

- 生成命令见第 8 节；明文只显示一次。
- **必须**在密码管理器里**另存一份**：Vercel 的 Sensitive 变量创建后不可回读（**调研**），丢失 = 全部邮箱/`sub` 密文不可解、全部用户无法按 `sub` 找到（再登录会建**新**账号，旧账号行变成孤儿）；**会话与 PAT 仍然有效**（它们不依赖密钥）。Neon 的备份**不含**这个密钥。
- 不进仓库、不进日志、不进截图；不用 `vercel env pull`（会把密钥写成本地文件）。

### 4.7 轮换流程

见第 8.6 节运营手册。设计要点：

- `GEMARC_ACCOUNTS_KEYS="k2:<新>,k1:<旧>"`：**第一项是活动密钥**，其余只用于解密与（CSRF）校验。
- `rekey` 是显式 CLI（有 `--dry-run`），**幂等**、可断点续跑（只处理 `kid` 不是活动密钥的行），分批（每批 200 行）、每批一个事务。
- 旧密钥只有在 `rekey`（或 `status`）打印的 `key references:` 显示没有行仍引用旧 kid（`k1=0` 与 `enc:k1=0`）之后才移出。**没做完 `rekey` 就移出旧钥匙会被检测到**：应用在第一次用库时检查存储行引用的 kid 是否都在密钥环里，缺失则关闭失败（503 `GEMARC_ACCT_004`，不会悄悄为同一个人再建一个账号），`doctor`、`status`、`migrate`、`rekey` 也都会报告。
- 密钥环解析拒绝：长度不是 32 字节、不同字节值少于 16 种、同一材料出现在两个 kid 下、base64url 带 `=`（`keygen` 的输出总是合格的）；这些只拦手工拼的弱钥匙。**因为凭据不依赖密钥，移出旧密钥不会使任何令牌或会话失效**；因怀疑泄露而轮换时，可以直接把旧密钥移出（先 `rekey`，让 PII 迁到新密钥）。

## 5. 数据库结构

### 5.1 可移植性规则（SQLite 做测试、Postgres 做生产）

| 规则 | 原因 |
|---|---|
| 只用 `TEXT`、`INTEGER`；时间用**秒级 UTC epoch 整数**；布尔用 `INTEGER` 0/1 | 两个引擎的类型亲和与时区行为不同；不用 `timestamptz`、`BOOLEAN`、`BYTEA`/`BLOB`、`SERIAL`、数组、JSON 类型 |
| 密文、nonce、哈希全部存 **base64url 文本** | `BLOB` 与 `BYTEA` 的驱动返回类型不同（`bytes` vs `memoryview`） |
| 主键是应用生成的随机 `TEXT` | 不依赖自增 |
| SQL 只写 `?` 占位符；`db.py` 在 Postgres 后端翻译成 `%s`（并转义字面 `%`） | 两个驱动的占位符不同 |
| 可用：`ON CONFLICT (…) DO UPDATE`、`ON CONFLICT (…) DO NOTHING`、`RETURNING`、`INSERT … SELECT`、`IN (子查询 … LIMIT n)`、`CHECK`、`REFERENCES … ON DELETE CASCADE/SET NULL` | 本机 SQLite 3.49.1 与 Postgres 都支持（SQLite 要求 ≥ 3.35） |
| **不用** `DELETE … LIMIT`、`INSERT OR REPLACE`、`ILIKE`、`::` 转换、`NOW()`、`CURRENT_TIMESTAMP`（时间由应用传入） | 方言差异；时间由应用传入也让测试可注入时钟 |
| 迁移文件里一个语句可以跨多行；**一个语句在「最后一个非空白字符是 `;` 的那一行」结束，`;` 不出现在任何别处**（字符串、注释里也不行） | 运行器按这条规则拆分，不实现 SQL 解析器 |
| SQLite 后端每个连接执行 `PRAGMA foreign_keys = ON` | 否则级联不生效 |

### 5.3 迁移策略

- **显式 CLI 为主**：`python -m gemarc_mcp.accounts migrate`，用 `GEMARC_MIGRATE_DATABASE_URL`，没有则用 `DATABASE_URL_UNPOOLED`（直连）。`status` 只读，报告已应用/待应用、密钥引用、行数估计（不含 PII）。
- 每个迁移在**一个事务**里执行（Postgres 与 SQLite 都有事务性 DDL）；Postgres 上先 `SELECT pg_advisory_xact_lock(<固定常量>)`，两个并发的迁移不会交错；SQLite 用 `BEGIN IMMEDIATE`。
- 记录文件的 **SHA-256 校验和**；已应用的迁移其文件内容被改动 → 拒绝继续（`checksum mismatch`）。迁移**只增不改**。某条迁移语句失败（例如库里已有同名的外来表）报告为 `migration refused: statement_failed in <文件>`，事务整体回滚，**不再冒充「数据库不可用」**（连接中途断开也会落在这个原因下，重跑即可区分）。
- **可选的受保护自动迁移**：`GEMARC_ACCOUNTS_AUTO_MIGRATE=1` 时，**第一次数据库使用**才尝试补迁移（冷请求里做，持事务级锁）。默认关闭，因为应用角色按最小权限没有 DDL 权限；关闭时结构过旧 → `GEMARC_ACCT_003` + `/healthz` 为 `db-unreachable`。它**不**碰已有迁移、**不**降级，不满足条件即 503。
- 迁移文件放 `src/gemarc_mcp/accounts/migrations/NNNN_name.sql`；`pyproject.toml` 的 `package-data` 需要加 `accounts/migrations/*.sql`（Vercel 因 `includeFiles: src/**` 本来就带；这条是给 wheel 用的）。

### 5.4 最小权限角色（评审后更正）

| 角色 | 用途 | 权限 |
|---|---|---|
| 拥有者（Neon 集成默认角色，名称由集成设置） | **只**用于迁移与运维 CLI（直连地址，在**你的机器上**使用） | DDL |
| `gemarc_app`（运营者在 Neon 控制台新建） | **函数运行时**（池化地址，放进 `GEMARC_ACCOUNTS_DATABASE_URL`） | 对本 schema 的 `USAGE`，对这 7 张表的 `SELECT, INSERT, UPDATE, DELETE`；**无** DDL、无 `TRUNCATE`、无创建角色 |

授权语句在第 8.8 节给出。

**必须如实写出的限制（旧稿说「运行时即使被注入也无法改表结构」是错的）**：Neon 集成默认把**拥有者**连接串（`DATABASE_URL`、`DATABASE_URL_UNPOOLED`）注入**同一个 Production 环境**，函数读得到它们；被攻破的函数可以直接从 `os.environ` 读出拥有者 URL。所以**仅仅**新增 `GEMARC_ACCOUNTS_DATABASE_URL` 并不能让运行时失去改表能力，它只能挡住「以应用角色身份执行的 SQL 注入/应用层漏洞」（T5），挡不住环境变量被读（T6）。要得到真正的最小权限，必须二选一：

- **(a)**（推荐，也是默认要求）：迁移完成后，把拥有者变量从项目的 **Production 作用域移除**（或者一开始就**不把存储连接到函数环境**，只手工添加 `gemarc_app` 的连接串为 Sensitive 变量）；集成是否允许移除、移除后是否会被重新注入 **UNVERIFIED**，第 8.8 节要求你检查。迁移需要拥有者 URL 时，从 **Neon 控制台**复制到本机当前会话（第 8.7 节），而不是从 Vercel。同时运行时在第一次用库时**检测**自己的角色（第 3.10 节）：判为 `privileged` → `GEMARC_ACCT_004`，**除非**运营者明示 `GEMARC_ACCOUNTS_DB_ROLE_RELAXED=1`。
- **(b)**：明确接受「运行时持有拥有者凭据」（设 `DB_ROLE_RELAXED=1`），在隐私/风险说明里如实写出；此时应用角色只是纵深防御的一层，不要宣称运行时无法改表。

不要删除集成使用的角色（删除会使预览分支创建失败，**调研**）。CLI `status` 报告检测到的角色类别（`privileged`/`app`，不输出名称）。

### 5.5 `SET LOCAL` 与事务边界

每个工作单元 = 一个事务：连接 → `SET LOCAL statement_timeout` → 业务 SQL → 提交 → 关闭。**事务内不做网络调用**（换码在事务**之外**完成，拿到声明后再开事务写库）。

### 5.6 机会式清理

没有常驻进程。成功的登录回调与令牌创建会顺带执行**有界**清理（每实例至多每 5 分钟一轮，实现在 `retention.py`；每类最多 200 行，`DELETE … WHERE id IN (SELECT id … LIMIT 200)`）：过期的 `oauth_states`、过期超过 1 天的会话、过期窗口之外的 `rate_limits`、早于保留期的 `audit_log`、撤销/过期超过 30 天的令牌。CLI `gc`（已实现）循环到没有可删为止。

**保留承诺的诚实边界（评审后）**：因为清理靠流量触发，第 1.2 节的保留期都是「**最长 N 天，前提是服务有流量**；没有流量时要等下一次 `gc`」。要硬保证，运营者需要自己定期运行 `python -m gemarc_mcp.accounts gc`（例如用本机的计划任务；由你决定频率）。

**为什么不在本期加 Vercel Cron（有意拒绝评审的另一个选项，D121）**：Cron 需要在 `vercel.json` 里声明，而 `vercel.json` **不在本任务允许修改的文件名单里**；它还要一个带 `CRON_SECRET` 校验的受保护清理端点，是新的鉴权面。**这是一个遗留事项**（第 10.1 节与 notes 的 Open issues）：若运营者希望硬保证保留期，应在后续任务里放行 `vercel.json` 再加。

### 8.2.1 连接串的 TLS 写法（**最可能的首次部署失败点**）

Neon 与 Vercel Marketplace 注入的连接串形如 `postgresql://…-pooler….neon.tech/db?sslmode=require`。**本应用的配置检查会拒绝它**（`sslmode=require` 只加密、不验证服务器证书）：
`GEMARC_ACCOUNTS=1` 之后 `/healthz` 显示 `accounts: "misconfigured"`，要求登录时 `/mcp` 答 503（关闭失败，不是故障）。按下面的顺序试，**每一步先在你自己的机器上用 `doctor` 验证**：

1. 把连接串改成 `…?sslmode=verify-full&sslrootcert=system`。`system` 是否被 `psycopg[binary]` 自带的 libpq 与 Vercel 运行时的 CA 库支持 **UNVERIFIED**（我们没有在真实 libpq 上试过）。
2. 不支持就保留 `sslmode=require`，并设置 `GEMARC_ACCOUNTS_DB_TLS_RELAXED=1`：明示接受「连接加密但不认证服务器」的风险（残余风险 R15），把这个决定记进你的风险说明。

`python -m gemarc_mcp.accounts doctor` 与 `status` 在遇到 `tls_insecure` 时会直接打印这条提示（只打印变量名与原因，不打印连接串）。

### 8.3 创建 Google OAuth 客户端

> 控制台的界面名称近年有调整（「Google Auth Platform」下的 Branding/Audience/Clients 等），以 Google 当前页面为准 **UNVERIFIED**。

1. 打开 Google Cloud 控制台 → 新建（或选择）一个**专用项目**，例如 `gemarc-login`。
2. **同意屏幕**：用户类型选 **External**；应用名称、用户支持邮箱、开发者联系邮箱必填；范围只加 `openid`、`email`（本设计**不请求** `profile`；这些是非敏感范围，**调研**）。
3. **决策点：发布状态与域名（评审后新增，请在投入下面的配置前先决定）**（**UNVERIFIED**，按调研整理）：
   - **Testing（测试中）**：只有你在「测试用户」里**手工列出**的账号（约 100 个上限）能登录。此时「注册」**实质上是邀请名单**：请同时设 `GEMARC_ACCOUNTS_ALLOWED_EMAILS`，并如实告诉用户这不是开放注册。适合先验证。

5. **已获授权的重定向 URI**（必须**逐字**一致，不能通配，不能带多余的 `/`）：

### 8.4 生成密钥环（PowerShell 5.1；值只显示一次，立刻存进密码管理器）

```powershell
$b = New-Object byte[] 32
[Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b)
'k1:' + ([Convert]::ToBase64String($b).TrimEnd('=').Replace('+','-').Replace('/','_'))
```

最省事的写法：`python -m gemarc_mcp.accounts keygen --kid k1`（只打印到屏幕，不写文件）。等价的 Python 写法：`python -c "import secrets; print('k1:' + secrets.token_urlsafe(32))"`（43 个字符 = 32 字节）。输出形如 `k1:XXXXXXXX…`，**整串**（含 `k1:`）就是 `GEMARC_ACCOUNTS_KEYS` 的值。

### 8.6 更换密钥与丢失

**计划内轮换**（建议每年或怀疑泄露时）：

1. 生成新密钥 `k2`（第 8.4 节，把 `k1` 改成 `k2`）。
2. 把变量改为 `k2:<新>,k1:<旧>`（`env rm` 后重新 `env add`）→ 重新部署。此后新写入用 `k2`，`k1` 仍可解密。
3. 运行 `python -m gemarc_mcp.accounts rekey --dry-run`，确认数量，再不带 `--dry-run` 运行：所有密文与盲索引迁到 `k2`。
4. 看 `rekey` 输出末尾的 `key references:`（`status` 也打印同一行）：确认 `k1=0` 与 `enc:k1=0`。**在此之前不要把 `k1` 移出变量**：否则应用会拒绝服务（503 `GEMARC_ACCT_004`，第 4.7 节）。
5. 满足 4 之后把变量改为只含 `k2` → 重新部署；旧密钥从密码管理器里标记作废。
6. **令牌与会话不受轮换影响**：它们用无密钥的 SHA-256（第 4.5 节），所以不需要通知用户重发令牌。怀疑**密钥泄露**时可以跳过「保留旧钥匙」的等待，直接 `rekey` 后移出旧钥匙；若同时怀疑**令牌**被盗，另行对相关用户执行 `disable-user` 或让他们 `revoke-all`。

**密钥丢失**：所有邮箱/`sub` 密文不可解、按 `sub` 找不到用户（再登录会建**新**账号）；**会话与 PAT 仍然有效**。唯一的补救是**从密码管理器恢复**。若确实丢失，只能由你以拥有者身份在 Neon 控制台的 SQL 编辑器里执行 `DELETE FROM users;`（级联删除会话与令牌）后让大家重新登录（`purge-user` 一次只处理一个用户，按邮箱找人还要用密钥，密钥丢了只能用 `--id`），这是**有意**的最坏情形，所以第 4.6 节要求另存备份并定期做一次恢复演练。

**客户端密钥泄露**：在 Google 控制台为该客户端重置密钥 → `env rm`/`env add` → 重新部署。

### 8.8 最小权限角色与拥有者变量的处理（**启用账号之前必须完成**；评审后前移）

> 这一步在第 8.7 节（迁移）之后、第 8.9 节（启用）之前。旧稿把它放在启用之后，并声称「此后运行时即使被注入也无法改表结构」，那个说法是错的（第 5.4 节）；现在它是启用前的**步骤 0**。

1. 在 Neon 控制台**新建角色** `gemarc_app`（让控制台生成口令，放进密码管理器），然后在 SQL 编辑器里以拥有者身份执行（迁移之后）：

   ```sql
   GRANT USAGE ON SCHEMA public TO gemarc_app;
   GRANT SELECT, INSERT, UPDATE, DELETE ON
     users, sessions, api_tokens, audit_log, rate_limits, oauth_states, schema_migrations
     TO gemarc_app;
   ALTER ROLE gemarc_app SET statement_timeout = '5s';
   ```

2. 用该角色构造**池化**连接串，并把 TLS 参数改成 `sslmode=verify-full&sslrootcert=system`（Neon 页面给的是 `sslmode=require`；`system` 是否被 `psycopg[binary]` 自带的 libpq 与 Vercel 的 CA 库支持 **UNVERIFIED**，第 8.11 节测它；不支持时的退路是保留 `sslmode=require` 并设 `GEMARC_ACCOUNTS_DB_TLS_RELAXED=1`，明示接受只加密不认证服务器的风险）。设为 `GEMARC_ACCOUNTS_DATABASE_URL`（`--sensitive`）：

   ```powershell
   npx vercel@65.8.0 env add GEMARC_ACCOUNTS_DATABASE_URL production --sensitive
   ```

3. **从项目的 Production 作用域移除拥有者变量**（`DATABASE_URL`、`DATABASE_URL_UNPOOLED`，以及旧集成的 `POSTGRES_URL`）：Vercel 控制台 → 项目 Settings → Environment Variables，或 `npx vercel@65.8.0 env rm <名称> production`。**集成是否允许移除、移除后会不会被重新注入 UNVERIFIED**：做完后用 `npx vercel@65.8.0 env ls production` **只看名称**核对。以后需要拥有者 URL（迁移、`rekey`）时，**从 Neon 控制台复制**到本机当前会话（第 8.7 节），不要从 Vercel 取。
4. 如果集成**不允许**移除（或会被重新注入）：不要假装解决了——二选一：**(a)** 不把存储连接到这个项目的函数环境，改用只含 `gemarc_app` 的手工变量；**(b)** 明示接受「运行时持有拥有者凭据」，设 `GEMARC_ACCOUNTS_DB_ROLE_RELAXED=1`，并在你的风险说明里写明。
5. **运行时角色检测看的是「连接用的角色」，看不到环境里还躺着什么变量**，所以第 3 步是**人工步骤**，靠第 8.11 节清单核对。启用后用 CLI `doctor`（它打印 `runtime role class`）确认角色类别为 `app`。

### 8.9 暂存部署、提升与验证（沿用 OPS-001 第 8、12 节的流程）

1. 先**不设** `GEMARC_ACCOUNTS`，部署一次，确认**默认行为不变**：

   ```powershell
   npx vercel@65.8.0 deploy --prod --skip-domain --yes --logs
   # 对暂存 URL 用 `vercel curl` 做冒烟（语法见 `npx vercel@65.8.0 curl --help`）
   ```

   `/healthz` 里**没有** `accounts` 键，`scripts/verify_remote.py` 全 PASS。**注意**：`--prod --skip-domain` 的暂存部署用的是 **Production 环境**，所以它的独立 URL 也同样服务 `/mcp` 与 PAT 校验、连着同一个数据库（只是账号页因 `Host` 检查返回 421）。
2. 提升该部署（`npx vercel@65.8.0 promote <deployment-url> --yes`）。此时线上仍是无账号形态，**可随时回退**。
3. 设置 `GEMARC_ACCOUNTS`（值输入 `1`，不带空格、引号或换行）：

   ```powershell
   npx vercel@65.8.0 env add GEMARC_ACCOUNTS production
   npx vercel@65.8.0 deploy --prod --skip-domain --yes --logs
   ```

4. 对暂存部署：`vercel curl /healthz` 期望 `accounts: "ok"`；若是 `misconfigured`，**公开的 `/healthz` 不会告诉你缺哪个变量**（有意，第 3.6 节），请在你的机器上用 `python -m gemarc_mcp.accounts status`（装有相同环境值的会话里，或按其提示）查看**缺失的变量名**，补上后重新部署。**暂存部署无法完整测登录**（重定向地址指向生产别名，别名此时还指向旧部署），所以再 promote。
5. promote 后，在浏览器里验证：
   - 打开 `<GEMARC_ACCOUNTS_BASE_URL>/account` → 先看到**告知文字** → 点「使用 Google 登录」→ 选 Gmail 账号 → 回到 `/account`，看到你的邮箱；
   - 创建一个 `read` 令牌（要求近期登录；只显示一次，存进密码管理器）；
   - `python scripts/verify_remote.py <GEMARC_ACCOUNTS_BASE_URL> --token <PAT>`（`GEMARC_MCP_AUTH` 为 `pat`/`pat-or-env` 时应全 PASS；用错令牌应 FAIL 在 401 项）；
   - 登出再访问 `/account` 应是未登录页；撤销令牌后 ≤ `PAT_CACHE_SECONDS`（默认 30 秒）该令牌得 401。
6. 满意后再决定是否收紧 `/mcp`：设 `GEMARC_MCP_AUTH=pat-or-env`（或 `GEMARC_REQUIRE_LOGIN=1`；**只能写 `1`**）→ 重新部署 → 复验。**这一步会把没有令牌的 claude.ai 连接器挡在外面**（第 3.6 节）。**如果这一步之后 `/mcp` 对所有人 503**：说明开关值或配置有误（这是关闭失败，不是故障），用 CLI `status` 看原因。
7. **回退**：删除 `GEMARC_ACCOUNTS`（以及 `GEMARC_MCP_AUTH`/`GEMARC_REQUIRE_LOGIN`）后重新部署，或 promote 上一个部署；数据库里的数据保留。**注意**：只删 `GEMARC_ACCOUNTS` 而留着 `GEMARC_REQUIRE_LOGIN=1` 会让 `/mcp` 503（不会退回开放），回退要把这三个一起处理。

### 8.11 上线后核对清单（评审后新增；这些都是 **UNVERIFIED** 项，必须在真实环境里测）

对生产别名逐项执行，每一项记录「通过/不通过/退路」：

1. **伪造转发头**：从同一台机器连续向 `<别名>/auth/google/start` 发 25 次 `curl -s -o /dev/null -w "%{http_code}
" -H "x-vercel-forwarded-for: 203.0.113.<每次不同>" -H "x-forwarded-for: 198.51.100.<每次不同>" <别名>/auth/google/start`（不跟随重定向；每次会写一行 10 分钟后过期的 `oauth_states`）。若第 21 次前后开始得到 429（限额 20 次/10 分钟/IP）→ 平台覆盖了伪造值，按 IP 的限流成立（预期）；若始终不出现 429 → 平台**没有**覆盖客户端自带的头，**不要依赖按 IP 的限流**，改靠 Vercel Firewall（第 3.7 节）。
2. **数据库 TLS**：确认 `sslmode=verify-full&sslrootcert=system` 能连上 Neon；连不上则采用退路（`require` + `DB_TLS_RELAXED=1`）并记入风险说明（R15）。
3. **拥有者变量已移除**：`npx vercel@65.8.0 env ls production` 里**看不到** `DATABASE_URL`、`DATABASE_URL_UNPOOLED`、`POSTGRES_URL`（或你已按第 8.8 节第 4 步选择了明示接受）；`doctor` 报告运行时角色类别为 `app`。
4. **Deployment Protection**：确认**生产别名没有**被 Deployment Protection（SSO/密码保护）覆盖。原因：Google 的回调必须能从公网到达，MCP 客户端也需要公开的 `/mcp`；一旦覆盖，登录与客户端都会被挡，还得把保护绕过密钥写进每个客户端配置。同时记住：`--skip-domain` 暂存部署的独立 URL 也服务 `/mcp` 与 PAT 校验（可选 `GEMARC_ACCOUNTS_MCP_HOST_ONLY=1` 削减这一面）。
5. **Vercel Firewall 限速与 Attack Challenge Mode**：确认你的套餐能给 `/auth/*`、`/account*`、`/mcp` 配限速规则（**UNVERIFIED**）；演练一次「开启 Attack Challenge Mode」作为紧急开关，并确认它对 MCP 客户端的影响。
6. **RS256 验签**：把 `GEMARC_ACCOUNTS_VERIFY_SIG` 设为 `1` 的暂存部署上，测一遍登录的耗时与 JWKS 抓取是否可靠；可靠再正式开启（第 3.3 节）。
7. **Google 的 `prompt=login` / `max_age`** 是否被遵守并返回 `auth_time`（第 3.5 节）：有效才把它用于 step-up。
8. **备份保留窗口**：第 8.2 节第 6 步记下的数字已写进你的隐私说明。
10. **受信 IP 与按 IP 的 DB 限额**：只有第 1 项的自检得到 429，才说明按 IP 的限额在生效。非 Vercel 主机必须设 `GEMARC_ACCOUNTS_TRUSTED_PROXY_HOPS`，否则启动日志与 `doctor` 都会有 `no_trusted_client_ip` 警告。
11. **单一主机**：账号路由只认 `GEMARC_ACCOUNTS_BASE_URL` 的主机名；预览/部署地址得到 421。只在生产别名上测试登录。
9. **`psycopg[binary]` 轮子**在 Vercel 构建日志里是否装上（**UNVERIFIED**，第 9 节退路 `pg8000`）；`DATABASE_URL`/`POSTGRES_URL` 的实际变量名；环境变量生效时机。

### 8.12 运营者命令一览（`python -m gemarc_mcp.accounts <命令>`；都不打印密钥、连接串或邮箱）

| 命令 | 作用 |
|---|---|
| `keygen [--kid k1]` | 打印一条新的密钥环条目（只到屏幕） |
| `migrate` | 应用待执行的迁移（`GEMARC_MIGRATE_DATABASE_URL` 或 `DATABASE_URL_UNPOOLED`）；密钥环在手时额外提示缺失的 kid |
| `doctor` | 配置、密钥环自检、连通性、结构版本、运行时角色类别、临时行往返、密钥环是否覆盖存储行 |
| `status` | 只读概览：配置问题与警告（变量名+原因+提示）、结构状态、各状态用户数与 `can_write` 数、`key references:`；有事项需要处理时退出码为 1 |
| `rekey [--dry-run]` | 把行迁到活动密钥；发现行引用了不在密钥环里的 kid 时报错并退出码 1 |
| `gc` | 保留清理（审计、限流、会话、令牌、OAuth 状态）循环到清空；保留天数取 `GEMARC_ACCOUNTS_AUDIT_RETENTION_DAYS`（默认 30） |
| `reconcile [--dry-run]` | 停用当前策略（`GEMARC_ACCOUNTS_ALLOWED_DOMAINS`/`_EMAILS`）不再允许的活动用户（同事务删会话、吊销令牌） |
| `disable-user` / `enable-user` | 停用 / 恢复登录（令牌不会恢复），用 `--id <32 位十六进制>` 或 `--email <地址>` |
| `grant-write` / `revoke-write` | 允许 / 撤销该用户创建 `write` 令牌（还要 `GEMARC_ALLOW_WRITE=1` 且工具集含写工具，第 3.4 节） |
| `purge-user --yes` | 硬删除一个用户及其会话、令牌，审计行匿名化 |

**定期做的事**：没有 Cron，保留清理在有登录/建令牌流量时顺带执行；要硬保证保留期，请自己定期跑 `gc`（例如每周一次）。

### 10.2 残余风险（逐条诚实列出）

| # | 风险 | 说明 |
|---|---|---|
| R1 | **库 + 环境同时泄露 = 全部 PII 明文** | 字段加密只把两者分开；密钥与密文在同一个 Vercel/Neon 信任边界内被两个事件各泄露才会解开；没有 KMS。**凭据（会话、PAT）不在此列**：它们不依赖密钥 |
| R2 | **硬删除与备份** | Neon 备份与时间点恢复在保留窗口内仍含已删行；共享主密钥的字段加密**不是密码学擦除**；窗口长度必须由运营者读出并写进隐私说明（第 8.2 节） |
| R3 | 令牌泄露窗口 | PAT 被泄露后到被撤销之间有效（默认最长 30 天，运营者可调到 90–365）；撤销另有最多一个缓存 TTL 的延迟 |
| R4 | **浏览器 Cookie 被窃取并被升级** | 会话可被带走直到过期（≤ 8 小时）；窃取者在 Google 会话仍存活的浏览器里可静默通过「近期登录」并铸造 PAT（近期登录**不是强重认证**，第 3.5 节）。叠加的缓解：默认 30 天、`token_created` 审计与「最近使用」、`revoke-all`、`logout-all`。**不要把它理解成「Cookie 被盗最多影响 8 小时」** |
| R5 | 默认不验签的 ID 令牌 | 默认依赖 TLS 链与 CA（CA 在 Vercel 运行时的可用性 UNVERIFIED）；`VERIFY_SIG=1` 后依赖 JWKS 抓取，上线实测后开启 |
| R6 | Google 侧失误 | 误发令牌、`email_verified` 错误；本设计信任 Google |
| R7 | 固定窗口限流的边界突发与分布式来源 | 无法完全防住对免费档算力的消耗；平台层 Firewall 限速的可用性 UNVERIFIED |
| R8 | Neon 缩零冷启动与 PAT 模式的常开 | 影响 `/mcp`（PAT 模式）首个请求延迟与免费档算力小时；缓存减轻但不消除 |
| R9 | 单点密钥 | 丢失 = PII 密文不可解、按 `sub` 找不到用户；凭据仍有效；依赖运营者备份 |
| R10 | 有库写权限者可改审计 | 没有防篡改链或外部日志 |
| R11 | **运行时可能持有拥有者凭据** | Marketplace 集成默认把拥有者连接串注入 Production 环境；除非按第 8.8 节移除，否则被攻破的函数能读到它并改表结构。「应用角色」只防应用层 SQL 注入类问题 |
| R12 | 平台行为未验证 | 环境变量生效时机、`x-vercel-forwarded-for` 是否被覆盖、`psycopg[binary]` 轮子、PgBouncer 事务模式行为、Neon 变量名（`POSTGRES_URL`）、`sslrootcert=system` 支持、Vercel 请求日志是否含查询串、Firewall 套餐、Google 发布规则，全部 **UNVERIFIED** |
| R13 | claude.ai 连接器进不了受保护的 `/mcp`；客户端要持有长寿命令牌 | 需要 OAuth 2.1，下一期 `accounts-oauth` |
| R14 | 邮箱可枚举的盲索引 | 密钥环泄露后可对候选邮箱离线验证 |
| R15 | **TLS 退路下的主动中间人** | 若 `sslrootcert=system` 不可用而采用 `require` + 明示，数据库连接只加密不认证服务器 |
| R16 | **`full` 工具集下的共享工作区** | 所有已登录用户共享一个服务器工作区、无隔离；`ACK_SHARED_WORKSPACE=1` 是明示接受，不是缓解 |
| R17 | **默认开放注册 = 任何 Gmail 持有者都能拿到只读令牌** | 默认策略是问责不是访问控制；限制访问必须设 `ALLOWED_EMAILS` |
| R18 | 保留期依赖流量 | 清理已接线（登录与建令牌后触发，每实例至多每 5 分钟、每表每轮至多 200 行；CLI `gc` 已实现），但没有流量时不会自动发生，需运营者定期 `gc`（遗留事项：没有 Cron） |
| R20 | **Postgres 路径未对真实服务器验证** | 驱动导入、TLS、池化、方言、角色检测、`pg_advisory_xact_lock`、连接错误到 503 的映射都只经过假驱动；上线前必须在一次性本地 Postgres 或 Neon 分支上运行 `pgcontract_run.py` 与 `test_pg_integration.py`，并跑 `doctor`/`migrate` |
| R21 | 无可信 IP 时按 IP 的 DB 限额不生效 | 非 Vercel 且无 hop 数，或 Vercel 上缺头；改用内存预过滤（连接地址+UA+Accept 的哈希键），客户端改头即可换桶，只是负载保护 |
| R22 | （已解决）`requirements.txt` 已同步新依赖 | 剩余风险：`psycopg[binary]` 在 Vercel 构建镜像上的安装未验证，需暂存部署确认（第 9 节） |
| R23 | 注册额度可被分布式来源耗尽；用户上限含停用行 | 全局 60/小时是共享额度，很多 IP 各注册几个即可耗尽；`MAX_USERS` 数所有行 |
| R19 | 惩罚通道的 429 | 攻击者占满同一 IP 的惩罚通道时，缓存未命中的有效令牌可能收到一次 429，重试即可 |
