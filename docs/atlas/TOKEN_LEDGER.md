# GemArc Atlas：token 账本重新测量（里程碑 M8）

本文件把设计 4.2 的「token 账本」放到真实的工具调用上重新量一遍。**量的是字节，不是 token**：脚本流水线里没有模型，所以每次调用的请求和回复有多少字节是实测，token 数只是用 `字节 / 3.2` 换算的估算，处处标明。真实的 token 数只能来自真实运行（API 报告的用量），那一节留空，由最终验收阶段填写（第 7 节）。

读这份账本之前要知道的一件事：**脚本流水线是一条没有弯路的路**。它一次写对每个切片、不修复、不回读、不思考，所以它的流量是真实运行的**下界**里最直接的那一部分，不是预测值。差别在第 5 节逐行写明。

## 1. 先看结论

- 参考规模（169 节点、374 边、242 证据、23 用例）：脚本经 38 次调用走到 done。**AI 要写出的字节** 183,522（估算 57,351 token，其中事实原文 178,471 字节），**AI 要读入的字节** 28,642（估算 8,951 token；这是 38 次工具回复之和，不含一次性的 tools/list 9,452 字节和入口提示 7,084 字节）。设计账本 4.2 对同一规模的目标值是 119,000 token（含 tools/list）：写的一侧吻合（事实原文按本账本的 字节 / 3.2 是 55,772 token，比设计的 slice text 行 57.4K 低 2.8%；按设计 4.2 自己的 字节 / 3 是 59,490 token，高 3.6%），读的一侧脚本远少于设计（设计 57.0K，这里 8,951，加上 tools/list 是 11,904），原因是脚本没有 index 回读、修复和揭示（第 5 节）。
- 事实原文的字节数与设计的预算一致：设计按 166 KB（±10%）估计参考规模的 `.atl`，实测 178,471 字节；请求的 JSON 转义多出 1.8%（3,287 字节），再加请求外壳（键名、项目名、切片名，1,296 字节）共 2.6%（4,583 字节）。
- 每次回复都在设计 4.1 的上限之内（`tests/atlas/test_pipeline_m8.py` 逐次断言）；参考规模最大的单次回复是 `gemarc_atlas_brief` 的 6,003 字节（设计上限 9 KB），其余工具里最大的是 `gemarc_atlas_review` 的 3,976 字节（上限 4.5 KB）。
- AI 从不写的派生物：参考规模下文档、图、提示词、oracle 表、页面和 `build-info.json`（1,895 字节，第 6 节的表里不单列）合计 2,623,501 字节，是 AI 写的事实的 14.7 倍；只看三层文档就是 2.61 倍（465,347 字节）。这部分如果让 AI 手写，输出量是事实原文的数倍，而且没有一致性保证（第 6 节）。
- 固定的一次性读入（tools/list、brief all、入口提示）合计 22,494 字节，估算 7,029 token，与规模无关。其中 brief 已经算在上面的 28,642 字节里（那次 `brief` 调用读到 en-US 的 6,003 字节，这里按 zh-CN 的 5,958 字节计），所以它不能和 28,642 相加。

## 2. 方法：哪些是实测，哪些是估算

| 数字 | 性质 | 来源 |
|---|---|---|
| 每次调用的请求字节（AI 写出的参数，紧凑 JSON，UTF-8） | **实测** | `tests/atlas/pipeline.py` 的 `Session.call` 在进程内调用已注册的工具函数（与 MCP 绑定同一套，含完成门，回复先过 20 KiB 的安全网），记录参数的 JSON 字节；`StdioSession` 走真实 stdio，回复字节取线上文本的长度 |
| 每次调用的回复字节（AI 读入的文本，紧凑 JSON） | **实测** | 同上；进程内的回复与 stdio 的回复经过同一套 `fit_result` 与紧凑 JSON 序列化，stdio 一侧的每次回复都在 `StdioPipelineTests` 里按设计 4.1 的上限断言。两边**只有构建出的页面**逐字节相同（断言页面 sha256 相同）；回复本身不逐字节相同：`init` 的回复带本机路径，`verify` 的回复带耗时 |
| 调用次数、阶段（orient、author、references、gates、review、final） | **实测** | 驱动脚本给每次调用标注阶段 |
| 生成物的字节（文档、图、提示词、页面、oracle 表） | **实测** | 构建后对 `atlas/dist/` 量 |
| tools/list、brief all、入口提示的字节 | **实测** | `tools/list` 经真实 MCP 服务器对象；brief 与提示由工具函数返回 |
| token 数 | **估算** | `字节 / 3.2`（混合文本：id 密集的 ASCII 行约 3 字节一个 token，CJK 散文每字约 1 到 1.5 个 token，设计 4.2 讨论过两个方向的偏差），不是任何分词器的输出 |
| 调用包装（工具名、`tool_use` 外壳） | **估算** | 沿用设计 4.2 的每次调用 35 token（[E]） |
| 设计账本 4.2 各行的 token | **设计的估算**（±30%） | `DESIGN.md` 4.2 目标列；按节点数线性缩放只是一个比较的尺子，不是预测 |
| 思考 token、修复轮、`index` 回读、读源码、API 报告的用量 | **未测** | 只有真实运行有；第 7 节 |

重现：

```
python tools/pilot/ledger.py                  # 五次运行，输出 JSON（约 1 分钟，含真实浏览器门）
python tools/pilot/ledger.py --markdown       # 本文第 4 节的表
python tools/pilot/ledger.py --no-browser     # 不跑浏览器门（verify 的回复就不在数字里）
python tools/pilot/asis_probe.py              # 在本仓库上量 outline（第 5 节末尾的真实 as-is 输入）
```

三份固定数据与两条作者流程都是合成的（`tests/atlas/synth.py`、`tests/atlas/pipeline_flows.py`）：tiny 是借阅台示例，small 约 40 个节点，reference 按参考规模（169 节点、374 边、242 证据、23 用例），greenfield 是一份虚构的社区菜园预约需求，as-is 是脚本生成的 25 个模块的仓库。fixture 的期望值来自引擎（它们是测试用的固定输入，不是 AI 的行为；见 `pipeline.py` 的说明），greenfield 与 as-is 的期望由需求和调用图写出。

对照读法：

- **写的一侧吻合**：事实原文的估算 token 与设计的 slice text 行相差在 3% 之内（reference：按本账本的 字节 / 3.2 是 −2.8%，按设计 4.2 自己的 字节 / 3 是 +3.6%，59,490 对 57,400；结论不变，但口径要写明），as-is 小图册按比例也在同一量级。写入量由事实的多少决定，与流程无关。
- **读的一侧差得远，而且是有原因的**：设计的读入合计 57.0K，其中 index 回读 18.8K、带修复的 put 回复 13.6K、oracle 揭示 8.7K，脚本里这三项是零或很小，因为脚本不犯错也不回读。真实运行的读入会落在脚本与设计之间，具体位置要由真实运行测出，不能用这里的数字预测。
- **设计 4.2 之外的两项**是 A1 加进来的审查（report 加 record，约 1,336 token）和入口提示（7,084 字节，估算 2,214 token，每次运行读一次）。
- **偏离**：tiny 与 greenfield 的脚本流量高于按节点数缩放的设计值，因为 tools/list、brief、提示词、review 报告是固定成本，缩放把它们也缩小了；小图册的账本不应按节点数线性缩放固定部分。

## 8. 限制和诚实说明

- tools/list 的字节数（9,452）是改完 `build` 的工具说明之后重新量的（integ-m8 那次运行量到 9,385，说明加了 67 字节）；其余字节数来自 integ-m8 的那次运行，没有因为这批改动重跑整本账本（重跑会因临时目录路径长度不同让 `init` 一行略有变化）。`test_ledger_tool.py` 把文档里的 tools/list 数字与当前代码量到的值对照，工具说明再变时它会失败，提醒重新量。
- 以上全是脚本的流量。脚本不思考、不犯错、不回读、不读源码，所以它不是 AI 的账本，而是 AI 账本里「必须经过工具的那部分」的实测。
- token 数是字节除以 3.2 的估算。CJK 比例高的文本（名称、说明、标题）每字符可能到 1 到 1.5 个 token，id 密集的 ASCII 行每 token 可能少于 3 字节，两个方向都会把真实数字推高（设计 4.2 讨论过）。
- fixture 里的期望值来自引擎，因为它们是合成的固定输入；不要把 fixture 的「一次通过」当成 AI 的首轮干净率。greenfield 与 as-is 的期望是按需求和调用图写出的，但作者（本脚本的作者）见过引擎，所以也不是盲写；盲写的比例要由 P1b 测。
- reference 与 small 的数据没有 as-is 的 `outline` 调用（它们的证据锚点由生成器给出，源码树由测试按锚点生成），所以第 4 节的 outline 行只出现在 as-is 运行里。
- 本文件由 `tools/pilot/ledger.py` 的一次运行生成。字节数在同一台机器、同样长度的路径下是确定的：`init` 的回复带工作区的绝对路径（本次 534 字节，路径更长时会多几十字节），`verify` 的回复带耗时数字，会让它差几个字节；换一个临时目录重跑，`init` 一行和合计会略有不同，其余不变。
