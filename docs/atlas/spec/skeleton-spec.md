# 文档骨架规范：每种元素的用途（不是字符串）

状态：**规范性（normative）**，适用于 `src/gemarc_mcp/atlas/derive/i18n/{zh-CN,ja-JP,en-US}.json`、`derive/policy.py`、`derive/prompts.py`、`derive/lint.py` 以及后续的文档构建通道。

结构标注（所有文档与界面必须原样使用，不得写成“IPA 标准”）：

| 语言 | 标注 |
|---|---|
| en-US | `IPA-inspired structure (not an official IPA template)` |
| zh-CN | `参考 IPA 的结构(非官方模板)` |
| ja-JP | `IPA を参考にした構成(公式の雛形ではありません)` |

本文只写**每个元素存在的目的**和**读者要从中得到什么**。三种语言的具体文字由实现者按这些目的各自撰写，不翻译、不改写任何外部文档的字符串；章节标题、表头、空状态文字、提示词与政策模板都以本文为唯一依据。字符串层的相似度检查（哈希拒绝名单与后续的片段相似度检查）把这个“从用途出发”的写法当作前提。

## 1. 一份文档是什么

REQ、BD、DD 三份文档共用同一套 12 个章节编号，越深的文档越细（`REQ ⊆ BD ⊆ DD`）：每个章节在更深的文档里是同一个编号的细化版，并在标题下写一行“细化关系”，让读者知道它承接上一层的哪一章。文档由固定代码从展开模型与选择范围导出，**作者（AI）只写事实**：模型里没有的值绝不被补全、猜测或默认，只显示显式标记（第 3 节）。

每个文档的 Markdown 形态是约定，lint（`derive/lint.py`）依赖它：

```
# <文档名> <文档编号>
<结构标注>
## <n>. <章节标题>          # n = 1..12，按序出现，每章一次
...正文...
```

- 章节标题行恰为 `## <n>. <title>`，`title` 取自骨架 `chapters.<level>.<n>`。
- 子节标题用 `###` 及更深，不会被当作章节。
- 表格是 GFM 表格；一切来自模型的文字都经过 `md_text` / `md_cell` 转义（第 6 节）。
- 对图表的引用写成 `[标题](dg:<单元 id>)`；对元素的引用写成行内代码 `` `<id>` ``。

## 2. 章节（12 章，三个层级）

每一项写“目的 / 事实来源 / 没有内容时怎么办”。标题文字在 JSON 里，每个层级可有不同标题（用途不同的章节），标题不同不改变编号。

| 章 | 目的 | 事实来源 | 空状态 |
|---|---|---|---|
| 1 文档管理信息 | 让读者知道这份文档是什么、针对什么范围、基于哪一版模型、处于什么状态。写出文档类型与层级、文档编号、上下层文档编号、模型版本戳（`model_sha8`）、审阅状态、对象摘要 | `meta`、选择范围 | 没有选择对象时写“未选择”，不是空白 |
| 2 本文定位与依据资料 | 说明目的与适用范围，并列出本文所依据的全部证据（谁说的、出自哪里、证明什么、可信等级） | 选择范围内全部元素的 `evidenceIds` 的并集，排序 | 引用了不存在的证据 id 时，该行保留 id 并标记未撰写，不得悄悄丢行 |
| 3 需求与追溯 | REQ：需求清单。BD：需求如何被组成部分落实。DD：BD 章节到本文章节的对照表、元素到章节的对照表、需求到设计与测试的追溯 | `requirements`、`tests` | 没有需求时写“选择范围内没有需求” |
| 4 结构 | REQ：相关方与业务范围（只含 `REQ` 级别的节点与它们之间的连接）。BD：可见节点与连接（含所在区域与可信度）。DD：逐节点、逐连接的细节（端口、基数、证据、数据与方法） | `nodes`、`edges`、`space` | 范围内没有节点时写“范围内没有组成部分” |
| 5 行为与场景 | REQ/BD：用例的业务含义、期望终态与期望结果。DD：逐用例的事件表与策略（超时、重试、退避），以及每个入口节点的进出边 | `cases`、`events` | 没有用例时写“未选择用例” |
| 6 数据 | 数据表：归属模块、底层存储、列。列的标记（主键、外键、唯一、必填、个人信息）是**数据**，来自 `props.columns`，不得由固定代码按名字猜测 | `Entity`、`Table` 节点 | 没有表时写“范围内没有数据表”；表缺列定义时写未撰写标记 |
| 7 外部接口 | 与外部的进出点：REQ 只列入口类连接；BD 列接口与端口的方向和类型；DD 逐端口列相连的边 | `edges`、`ports`、`nodes` | 没有入口节点时写“范围内没有外部接口” |
| 8 状态 | 每台状态机的状态、初始状态、终止状态、错误码、转移表（含守卫） | `machines`、所有者的 `owns` 边 | 没有机器时写“范围内没有状态机” |
| 9 非功能性要求 | 把非功能要求变成可追溯的条目。内容只来自 `kind=nfr` 的政策与它们的 `src` 需求。**没有任何 nfr 政策时写未撰写标记（发布前必须清零）**，不得用固定文字代替 | `policies` | 未撰写标记 `ch9.nfr` |
| 10 约束与待决事项 | 约束（`kind=constraint` 的政策）与全部待决事项（每一条 TBD 都必须出现，不论是否被需求引用） | `policies`、`tbds` | 没有约束时明确写“未声明约束”（这是明确状态，不是缺失）；没有 TBD 写“没有待决事项” |
| 11 验收与验证 | 验收条件、测试方针。验收条目是**机械地**从期望终态、期望结果、需求测试 id 导出，质量等于这些字段的质量，所以必须直说这一点 | `cases[].expected*`、`requirements[].tstIds`、`cases[].linkedTestIds` | 没有可导出的条目时写“没有可导出的验收条目” |
| 12 评审与批准 | 留给人的空白签署表（作成、评审、批准 × 担当、日期、结果）和一句判定说明。**设计上永远是空白**，因此不算缺失 | 无 | 固定内容，不会空 |

章节标题的撰写规则：同一编号在三个层级里可以不同（4 至 8、11 章的用途随层级变化）；第 1、2、9、10、12 章三个层级相同；任何标题不得出现业务领域名词。

## 3. 三种“空”必须被区分

读者不能从空白判断是“没填”还是“不适用”。每个空状态都带一个与语言无关的 ASCII 标记，使 lint 用同一个正则统计，旁边可以有本地化的说明文字：

| 标记 | 含义 | 出现在哪里 | 对发布的影响 |
|---|---|---|---|
| `[NOT-AUTHORED:<slot>]` | 这里需要一个事实，模型里没有（或类型错误）。`<slot>` 是字段位置，如 `node.sub@<id>`、`ch9.nfr` | 单元格、行、整章 | **阻断发布**（DC-L-004） |
| `[N/A]` | 这个槽位对该元素在结构上不适用（如不带守卫的转移的守卫列） | 单元格 | 无 |
| `[NONE-IN-SCOPE]` | 选择范围内没有这类元素 | 整章或小节，后跟一句话 | 无 |
| `[NONE-DECLARED]` | 这类可选记录没有被作者声明（如约束） | 整章或小节，后跟一句话 | 无 |

要求：用户文本里出现这些标记字面量时必须被转义（`[` 与 `]` 加反斜杠），使它们既不能伪造也不能掩盖标记。标记里 `<slot>` 的字符集限于字母、数字与 `._-@#:`，其余字符替换为 `_`，并截断到 60 字符。

## 4. “事实不是编造的”声明

每份文档的第 1 章末尾带一段固定声明，目的有三：（a）读者知道文字是机械导出的，每个陈述来自已作者的事实；（b）读者知道缺失会以 `[NOT-AUTHORED:…]` 显示而不是被补全；（c）读者知道验收条目是机械导出的，不是独立撰写的判断。在 JSON 里是 `facts_note` 数组，每行一个目的。

## 5. 表头

每个表只需要说明**读者拿它做什么**。列的用途如下（JSON 键在 `th.<name>`）：

| 键 | 读者用途 | 列（按序） |
|---|---|---|
| `evidence` | 核对依据 | 证据 id、出处（文件与行）、证明了什么、可信等级 |
| `requirement` | 看需求清单 | id、标题、来源、测试 |
| `coverage` | 看需求被谁落实 | 需求 id、标题、上层章节、设计引用、落实它的元素、测试 |
| `node_req` | 看业务级元素 | id、名称、种类、一句说明、相关需求 |
| `node_bd` | 看架构元素 | id、名称、种类、一句说明、所在区域、可信度、相关需求 |
| `edge_min` | 看业务级连接 | id、起点、终点、关系、标签 |
| `edge_bd` | 看架构连接 | id、起点、终点、关系与基数、标签、可信度 |
| `edge_dd` | 看连接细节 | id、起点、起点端口、终点、终点端口、关系、基数、守卫、证据、可信度 |
| `case` | 看用例 | id、标题、类别、相关需求、期望终态 |
| `event` | 看用例的事件序列 | 序号、类型、起点、终点、步骤名、参数与选项 |
| `entity` | 看数据表 | id、名称、归属模块、底层存储、列数 |
| `column` | 看列的数据 | 列名、类型、标记、备注 |
| `port` | 看端口 | 节点、方向、类型、相连的边 |
| `transition` | 看状态转移 | id、起点状态、终点状态、守卫、错误码 |
| `tbd` | 看待决事项 | id、标题、决定、依据 |
| `policy` | 看政策条目 | 正文、来源、作者（ai 或 user） |
| `exception` | 看异常结果 | 步骤名、结果、错误码、用例 |
| `testplan` | 看验证安排 | 需求或用例、测试 |
| `crossmap` | 看上层元素在本章的位置 | 元素 id、名称、上层章节、本文章节 |
| `signoff` | 空白签署表 | 角色、担当、日期、结果 |

## 6. 文字卫生（对应设计风险 14）

来自模型的任何文字进入 Markdown 前都要中和：`|` 转义；换行、回车、制表符变成一个空格；反引号与围栏（三个以上的反引号或波浪线）被中和；`[` `]` `<` `>` 转义（防止链接、图片与 HTML 注入，也防止伪造标记与 `dg:` 链接）；控制字符删除。进入 Mermaid 的文字只出现在带引号的标签或经过清理的成员行里，引号、`<`、`%%`、反引号、换行与大括号被中和。提示词里的节点文字同样经过这些处理。不得用 `str()` 或字符串插值输出字典或可能为空的值，结构化值一律用 `json.dumps`（`null` 是合法输出）；字面量 `undefined`、`NaN`、`None`、`[object` 不得出现在任何生成物里。

## 7. 政策（`policies` 行）如何变成章节文字

- 一条政策只在它的 `level` 及更深的文档里出现。
- `scope`：`all` 总是出现；`kind:<Kind>` 在选择范围含该种类节点时出现；`node:<id>` 在该节点在范围内时出现；`req:<id>` 在该需求在范围内时出现。
- `chapter` 为 `null` 时取该 `kind` 的默认章：`constraint` 到第 10 章，`nfr` 到第 9 章，`data` 到第 6 章。
- 每条政策必须带 `src`（需求或待决事项）。条目文字后附 `src` 与作者类别；`by=ai` 的条数是质量报告里的**幻觉面**指标。
- 政策是项目的数据，不是骨架：骨架里不允许有任何领域断言（租户隔离、个人信息、错误码约定等一律没有）。

## 8. 提示词（6 种）

| 类型 | 目的 | 何时出现 |
|---|---|---|
| `REQ`、`BD`、`DD` | 让下游 AI 为所选对象撰写同层级的文档：给出目标、对象清单、根据（证据）、约束（政策与由数据派生的条目）、期望产物（章节清单）、验收条目、紧凑的事实上下文，并反复强调“只用这些事实，缺失写未撰写标记” | 总是 |
| `implement` | 让 AI 按设计实现所选元素，并给出所选用例及其已作者的期望状态 | 总是（作者自己写的期望不是裁决，不需要封存） |
| `test` | 让 AI 为所选用例写测试 | 仅当所选用例全部**已封存**（预言机通道提供） |
| `failure-analysis` | 让 AI 用可读的因果链解释一次差异，并回到设计章节说理 | 同上，并需要引擎结果 |

预言机通道尚未提供时，`test` 与 `failure-analysis` 恒返回**空状态**：一句“先写出期望”的说明，不输出任何提示词正文，也不输出任何期望值。提示词编号 = 类型、选择范围与 `model_sha8` 的哈希，同一选择在模型变化后得到不同编号。

## 9. 图表

文档只链接图表，图表文本是 Mermaid，由 `derive/diagrams.py` 从结构导出，**构建函数返回问题而不是抛异常**。单元种类 `component`、`class`、`state`、`er` 现在提供；`sequence` 在预言机通道之后加入，只对已封存用例生成，入口是 `mermaid.register_builder`。标题与未放置分组的说明文字在 JSON 的 `diagrams` 下。

## 10. 大小与完备性约束

- 每种语言的骨架（JSON 里的 `skeleton` 对象）3 至 6 KB（UTF-8 字节）；三个文件的键集合必须完全相同（测试断言）。
- 三种语言每个键都必须非空；禁止出现字面量 `undefined`、`NaN`、`None`、`[object`。
- 所有三个文件与本文都要通过 `tests/atlas/test_denylist.py`；若通用词被误判，改写为更通用的说法，改不了就报告，不得修改拒绝名单。
