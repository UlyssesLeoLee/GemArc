# Oracle: expectations are intent

- An `expect` row (and an intervention's `class` and `terminal`) states what SHOULD happen. Write it from the requirement or the code you read, before any simulation. Never copy an engine result into it.
- **How final states follow from events** (engine rules, not results). Every node starts `Idle`; the first event's `from` starts `Running`. A `Call` or `Message` makes its receiver `Running` (`Completed` with `ack`) and it STAYS `Running` unless a `Return` comes. `Return` makes its sender `Completed`; `Failure` makes its receiver `Failed`; exhausted retries make the receiver `Failed`; `Compensation` and `Recovery` make their sender `Recovered`. A source never reached cannot emit (skipped). A node no event touches stays `Idle`.
- **Sealing.** A write call (put, simulate, build) seals an expectation once every node it names is defined and every `outcomes` ruleId is carried by an event of the case. Otherwise it waits: the put reply says `oracle: waiting`, `simulate` answers `OR-000 not registered` with no verdict, `check` prints OR-000.
- **Verdicts are blind.** `simulate` (default `detail=count`) says pass or fail and how MANY asserted nodes differ, never which. Every failing verdict is recorded as a mismatch even if the reply cannot list it. `detail=ids` and `detail=trace` need a case or intervention and are reveals, recorded when shown. A verdict for a revised item says so: it does not count as sealed.
- **States.** `sealed`: registered before any result for it was shown; editing it before any result re-seals it in place. `revised`: edited (or deleted and added again) after a mismatch report, a reveal or a build that embedded its trace. Copies share this: cases with the same events (step names do not count) are ONE unit, so when one has a mismatch or reveal on record every other copy is `revised` at once; likewise interventions with the same deltas. Fixing the case EVENTS keeps `sealed`. `confirmed`: the user approved it. `by=user` counts only when confirmed.
- **Anti-vacuity.** Assert at least max(2, 35% of the participants) nodes (OR-003); Idle on a node the events never touch does not count; a case with an expectation but no events is vacuous. An abnormal, recovery or combination case that asserts only Completed gets OR-002. OR-004: a disabled participant or a deleted event must break the assertions, else they constrain nothing; the release gate needs that mutant run (`simulate --bite`; the release build makes it).
- **Done.** Every expectation sealed or confirmed with a passing verdict for this model (`simulate` after any change); `revised` ones need the user. The build writes `atlas/dist/oracle-sheet.md` (one line per unconfirmed expectation, plus APPROVE-ALL). The USER confirms in `atlas/oracle-confirm.txt`; you never write it, and never edit `.atlas/oracle.json` (a tampered ledger marks the project UNVERIFIED PROVENANCE).
- `check mode=full rule=OR` also shows OR-001, OR-004 and OR-005 from the ledger.
